## M0

- **License LGPL-2.1-or-later** — forced by transcribing XADMaster
  (LGPL) algorithms; see NOTICE.
- **`reference/` is gitignored**, repopulated by
  `tools/fetch_references.sh`. It contains a full LGPL repo clone plus
  fetched wiki text of unclear licensing; committing it would bloat the
  repo and muddy provenance. The fetch script *is* the provenance record.
- **Listing = extraction minus writes.** No separate `unc_list`
  allocation API: `UncOptions.list_only` drives the same streaming walk
  and reports entries via `begin_entry`/`end_entry`. One code path to
  test, no arrays to size, and the Mac app gets progress-capable
  listing for free. (`begin_entry` returning >0 means "skip data",
  which is also how listing is implemented.)
- **CRC tables are compile-time constants** generated from the
  documented polynomials (0x1021 XMODEM for MacBinary II/BinHex,
  reflected 0xEDB88320 for Arsenic/zip/gzip) with check values
  asserted in unit tests. XADMaster computes the XMODEM CRC through a
  reflected table + bit-unreverse dance (`XADCRCReverseTable_1021` +
  `XADUnReverseCRC16`); the plain MSB-first formulation is
  mathematically identical and simpler; equivalence is pinned by the
  standard check value 0x31C3 and by every MacBinary/BinHex fixture.
- **Engine emits raw archive-encoding names** (MacRoman for Mac
  formats); MacRoman→UTF-8 conversion is CLI-side (`--raw-names`
  opts out). Encoding choice is per-format at the frontend: Mac
  containers → MacRoman, zip/tar/gzip → pass-through.
- **Oracle manifests are built with `unar -nr` (no recursion)** so each
  manifest describes exactly one container layer. Nesting is tested by
  chaining layers, not by replicating unar's name-based recursion
  heuristics (XADMacArchiveParser recurses into MacBinary members only
  when the *name* matches /\.(sea|sit|cpt)$/ — a quirk, not a spec).
- **Manifest dates are not compared** (v1). Mac timestamps pass through
  XADMaster's timezone interpretation in the oracle; chasing an exact
  epoch match adds risk without validating any decompression code. The
  engine still surfaces raw 1904-epoch seconds; correctness of the
  *fields* is covered by the type/creator checks that ride the same
  header parses.
- **Allocator budget lives in the frontend callback**, not the engine:
  the engine just sees NULL and must fail per-entry. This keeps the
  budget policy (CLI `--budget`, Mac `FreeMem()`-driven) out of the
  engine and makes over-budget behavior mechanically testable.
- **`unc_skip` rejects offset wraparound** (`pos + len < pos`) as
  corrupt: all offsets are 32-bit by design (HFS caps files at 2 GB).

## M1

- **Oracle output is not blindly trusted:** `unar` (GNUstep build)
  mishandles resource forks when it cannot append `.rsrc` to a name
  (leading `~`, seen with `lipservice.bin` — our extraction was correct,
  the oracle's was not). `make_manifests.py` refuses to build a
  manifest when unar prints `cannot append extension`.
  **Narrowed 2026-08-08:** this is a `-k visible` bug — it is the
  *appending* that GNUstep refuses — and manifests are now built with
  `-k hidden`, under which `lipservice.bin` is ground truth like any
  other fixture. The refusal stays as a guard for a mode that should no
  longer be reachable.
- **MacBinary II/III CRC fallback:** XADMaster also accepts a
  CRC-16/USB-style checksum (reflected poly 0xA001, init/xor 0xFFFF)
  from buggy encoders; transcribed as a bitwise loop rather than a
  second table (runs over 124 bytes, speed irrelevant).
- **Envelope fixtures are "derived" corpus entries:** the payload of
  each BinHex/MacBinary fixture is extracted with the oracle and
  registered as its own fixture (`derived-*`, provenance
  `derived:unar-nr:<parent>` in SOURCES.md), giving per-layer ground
  truth for nested chains without replicating unar's name-based
  recursion.

## M2

- **BinHex sniffing reads beyond the 512-byte head:** real Info-Mac
  .hqx files bury the banner after mail headers/digest preambles
  (observed at offset 1270). The probe streams up to 8 KB (the same
  window XADMaster inspects) with a rolling 40-byte comparison.
- **Filename sanitization differences are normalized in the harness,
  not imitated:** for '/' in Mac filenames unar-on-Linux emits '_' while
  unclassic emits ':' (the classic Mac swap). `run_diff.py` maps
  [:/] → '_' on both sides, per path component. The engine still emits
  raw bytes.

## M3

- **PackIt trailing fork CRC is big-endian in both modes.** The
  references disagree for Huffman entries: macutils pit.c reads it
  little-endian (`getihuffbyte() | getihuffbyte() << 8`) while
  XADMaster reads it big-endian through the decode handle. Arbitrated
  with two further sources — unpit 0.3.1 (contemporaneous with PackIt;
  `getcrc()` is `(byte1 << 8) | byte2` for both modes) and the nocash
  PSX-SPX PackIt page — both big-endian. macutils' LE read is its own
  bug; `macunpack` therefore cross-checks only stored entries.
- **PackIt date fields:** creation @84, modification @88 (macutils
  pit.h H_CTIMOFF/H_MTIMOFF + nocash). XADMaster reads them in the
  opposite order (`modification` then `creation`) — presumed swapped
  there; harmless to us since manifests don't compare dates.
- **No real PMa4 fixtures exist** on the surviving mirrors (searched
  Info-Mac/funet/macgdn; every found .pit is stored-mode). Compressed
  coverage comes from `tools/synth_pit.py`: deterministic synthetic
  archives (provenance `synthetic:tools/synth_pit.py --seed N` in
  SOURCES.md, regenerated by `harvest.py --restore`), validated
  against the unar oracle like any harvested fixture.
- **Encrypted PMa5/PMa6 entries are reported and skipped** with the
  macutils resync strategy (byte-scan for the next block magic):
  without the password the entry length is unknowable. XADMaster's
  password-based decryption is out of scope (v1).
- **lsar JSON is parsed with `strict=False`:** its output can embed
  raw control bytes (binary `XADNextSolidEntry` values in PackIt
  archives), which the default Python JSON parser rejects.
- **Manifest builder synthesizes entries for orphan sidecars**
  (resource-only entries: unar writes nothing for a 0-byte data fork,
  so the data file is absent and only the sidecar — `._<name>` since
  2026-08-08, `<name>.rsrc` before it — exists).

## M4

- **Path model settled for hierarchical containers:**
  `UncEntryInfo.name` is a '/'-separated path. Mac name components get
  the classic reversible '/'→':' swap inside the engine (':' cannot
  occur in an HFS name, '/' can — so nothing is lost), and zip/tar
  paths will pass through natively. The CLI now treats '/' strictly as
  a separator and defuses '.'/'..' components; final on-disk names are
  unchanged for the single-entry formats.
- **CPT probe verifies the full index CRC** (as XADMaster's recognizer
  does): the 1-byte magic (0x01) is far too weak alone. The extractor
  then trusts the index and relies on per-file CRCs, avoiding a second
  full pass.
- **Index parsed via per-entry `unc_read_at`, no index preload:** the
  container interleaves index walking with fork decoding; random
  access keeps peak memory at ~17 KB (io + staging + 8 KB window)
  regardless of entry count.
- **LZH block padding transcribed from XADMaster**, not macutils:
  macutils' eager 16-bit refill implicitly skips 2–3 padding bytes at
  each 0x1FFF0-cost block boundary; XADCompactProLZHHandle expresses
  the same thing explicitly (align; skip 3 if odd bytes consumed since
  the previous trees, else 2) which fits our lazy bit reader.
- **RLE quirks preserved bit-for-bit** from macutils cpt_outch: an
  0x81 that would be the final output byte is a literal; 0x81 0x81
  emits a literal 0x81 while staying escaped; 0x81 0x82 0x00 is a
  literal "0x81 0x82". The 106-fixture corpus exercises all of them.
- **~~Oracle output can be structurally undecidable~~ — WITHDRAWN
  2026-08-08.** Claimed: archives holding both "X" and "X.rsrc" as real
  entries (THINK C projects) cannot be represented at all, so
  `derived-BootTime.cpt` and `derived-GNU_Chess_3.0.cpt` stay
  corpus-only. True of the `.rsrc`-suffix convention, and it was the
  convention that was chosen, not a property of the archives:
  `unar -k hidden` and `unclassic --forks hidden` name the sidecar
  `._X`, which collides with nothing. Both fixtures now have manifests.
  BLOCKERS.md *Withdrawn claims*; DECISIONS.md 2026-08-08.
- **`UncBufIn.limit`** bounds every compressed fork substream so
  corrupt streams cannot read into unrelated bytes — mirrors
  XADMaster's bounded sub-handles.

## M5+M6 (committed together)

- **M5 and M6 land in one commit:** the corpus interleaves methods —
  almost every classic .sit carries method 13 next to methods 0/2/3 —
  so an M5-only build cannot pass the full StuffIt differential suite,
  and CI must be green at every commit. Methods 0/1/2/3 were still
  built and validated first (211-fixture suite + unit tests), then
  13/5/8 added.
- **CRC-16/ARC** (reflected 0xA001, init 0) added for StuffIt header
  and fork CRCs; pinned against an independent bitwise implementation
  and the 0xBB3D check value in unit tests.
- **LZW lives in unc_lzw.c** (compress(1)-compatible, LSB-first
  codes): StuffIt method 2 is compress with 14-bit codes + block mode
  (XADStuffItParser passes flags 0x8e), and M8's .Z reuses the same
  decoder with header-supplied parameters. Compress quirks preserved:
  width grows at power-of-two table sizes; a clear code discards the
  rest of its 8-code group.
- **Method 13 fixed tables are machine-transcribed**
  (tools/gen_sit13_tables.py -> src/sit13_tables.h) from
  XADStuffIt13Handle.m — 3,270 table entries hand-copying of which
  would certainly have introduced errors. The generated header is
  committed so the build does not require reference/.
- **Method 13 is the one little-endian-bit-order format** in the
  classic Mac family; UncBitIn grew an LE mode instead of a second
  reader type. Found the hard way: UncCanon.first[] must be 32-bit —
  17-bit canonical codes overflow uint16 exactly at the point the
  method-13 "second" code needs them (dynamic codes reach length 17+,
  fixed tables reach 18).
- **Method 5 ("LZAH") transcribed from XADLZHDynamicHandle** — the
  handle the oracle actually runs — including its LHarc-style window
  preload (value runs + ramps + zeros + spaces), not from the disabled
  libxad SIT_lzah in the same file (all-spaces window, different
  offset coding). XADMaster's own TODO doubts the preload; our
  fixtures decode byte-exact against the oracle either way it settles.
- **Method 1 (RLE90) has no corpus fixture**; it is pinned by unit
  tests (including the 0x90 0x01 illegal-count case, per
  XADRLE90Handle).
- **StuffIt entry-header CRC failures abort the walk**
  (UNC_ERR_CORRUPT): headers chain by compressed lengths, so a bad
  header leaves no way to locate the next entry (XADStuffItParser
  raises a checksum exception at the same point).
- **`~`-name oracle bug generalized:** GNUstep unar can silently write
  the AppleDouble container INTO the data-fork filename (no warning
  printed), caught on derived-020_Simulator.sit; five more fixtures
  were dropped as .rsrc-collision undecidable (BitMap11, The_Journal,
  TogSndVol, Unzip101, unshar_1.11). **All six recovered 2026-08-08**
  when manifests moved to `-k hidden`: both defects belonged to the
  suffix convention. The AppleDouble-as-data-fork guard is replaced by
  its stronger form — every `._` sidecar must parse as an AppleDouble
  container, or the fixture is refused.

## M7

- **SIT5 entry-header CRC is not verified** (XADStuffIt5Parser reads
  and ignores it; per-entry sync is re-checked by the 0xA5A5A5A5 id on
  every header, and fork CRCs still guard the data). Russotto's doc
  describes the CRC but the oracle never enforces it.
- **Second-block prefix is 14 bytes** (u16 flags, u16 ?, u32 type,
  u32 creator, u16 finderflags) followed by a 22-byte (entry v1) or
  18-byte (v2+) skip — found the hard way after assuming 16.
- **SIT5's "mystery entries"** (datalen 0xFFFFFFFF after every
  directory) are skipped without consuming an entry slot, exactly as
  XADStuffIt5Parser does; directory parentage is tracked by header
  offset, not nesting order (bounded map, 256 dirs / 16 KB of path
  pool — overflowing dirs degrade to root-relative paths rather than
  failing).
- **Arsenic transform vector is sized to the actual block fill**, not
  the declared block size. Every real SIT5 fixture declares 512 KB
  blocks (blockbits 19) even for 3 KB payloads; allocating
  4 x blocksize up front would pin every extraction at ~2.6 MB.
  With lazy sizing the corpus measures: min 0.63 MB, median 0.97 MB,
  mean 1.23 MB, max 2.53 MB (fixtures that genuinely fill their
  blocks). A 1 MB Mac Plus can therefore expand small Arsenic archives
  but will cleanly refuse large ones per entry (UNC_ERR_MEM) — by
  design.
  **RE-CONFIRMED 2026-08-01, against a later entry that contradicted
  it.** The M10 entry below ("Arsenic block sizes are 128 KB
  (dominant) / 256 KB / 512 KB, not 'always 512 KB'") was the wrong one
  of the pair: instrumenting the point where `sit_arsenic.c` reads the
  block-size field shows all 484 Arsenic streams across the 31-fixture
  corpus — one per compressed fork — declaring 512 KB, without exception. This entry stands; only
  the precision of its figures has been sharpened.
- **Arsenic CRC-32 is internal to the stream** (read from the final
  block's end marker, compared against ~crc of the output); the SIT5
  header CRC-16 field is meaningless for method 15 and is skipped,
  as in XADMaster.
- **No synthetic Arsenic unit fixture:** producing one would require
  writing an arithmetic *encoder*; coverage comes from 31 real SIT5
  fixtures plus their 310 corruption variants.

- **zlib 1.3.1 vendored unmodified** (inflate subset only) into
  third_party/zlib; allocation is routed through UncAlloc via
  z_stream zalloc/zfree, so the engine's no-libc rule holds. Raw mode

- **Synthetic exogenous fixtures are encoded by independent reference
  implementations** — Info-ZIP zip, GNU gzip, GNU tar, ncompress —
  which is stronger ground truth than hand-built streams
  (tools/synth_exo.py; deterministic via TZ=UTC, fixed mtimes,
  gzip -n, tar --sort/--owner/--group/--mtime, zip -X). Plus
  real-world era files: PCCTS.tar.gz, popper-1.7.tar.Z,
  a2ps.V4.3.tar.Z from funet.
- **4acalc.zip / 4alnch11.zip (PKZIP 1.x, method Implode) exercise our
  clean per-entry "unsupported method" path and the robustness
  harness.** This said they stay corpus-only because "even unar fails on
  them"; unar fails on ONE entry of each, and since per-entry manifests
  landed (2026-08-08) both carry ground truth for the rest — 5 of 7
  entries. Corrected 2026-08-08, along with the harness that was
  skipping them whole (TESTING.md, "When our engine declines an entry").
- **gzip/.Z carry no entry name; unar derives it from the archive
  filename (minus extension), ignoring even an embedded FNAME.** The
  engine gained UncOptions.name_hint so frontends can supply the same
  convention; content-only sniffing is unaffected.
- **Zip is parsed from the central directory** (EOCD scanned in the
  last 66,000 bytes), with per-entry data offsets taken from each
  local header (their name/extra sizes can differ from the CD's).
  Methods other than store/deflate and encrypted entries are clean
  per-entry errors. zip64 is out of scope (HFS-era corpus).
- **tar acceptance requires a valid header checksum** (unsigned, or
  signed for old GNU tars); link/device/GNU-extension entries are
  reported per-entry as unsupported rather than silently skipped.

## M9 follow-up (real-tar coverage)

- **"Tested against known files" audit found the tar gap:** the only
  oracle-verified tar was synthetic; real tars in the corpus were only
  checked as .Z/.gz payload bytes. Deriving them as fixtures exposed
  two real bugs: (1) the probe demanded the "ustar" magic, rejecting
  every pre-POSIX v7 tar — and XADTarParser recognizes v7 only by
  *filename*, which our content-only rule forbids, so our v7 probe
  demands structure instead (checksum + octal field syntax + printable
  NUL-terminated name); (2) v7 marks directories only by a trailing
  '/' in the name (there is no '5' typeflag), and "./" name prefixes
  are routine — both now handled, and both 1990 tars
  (popper-1.7, PCCTS) extract byte-exact.
- Remaining known corpus gaps, unfixable for lack of surviving real
  files: PackIt PMa4 (synthetic only) and StuffIt method 1 (unit
  tests only). Recorded in FORMATS.md footnotes.

## M10 runtime verification (Mini vMac / System 6.0.8 / Mac Plus, 4 MB)

Ran the compiled app on a real emulated Mac Plus (Mini vMac 36.04,
System 6.0.8, 4 MB) driven via Xvfb + xdotool, with output verified by
reading the HFS image back with hfsutils. Findings:

- **Verified working on genuine 68000 hardware:** app launch, the full
  Toolbox UI (SFGetFile, volume navigation, modal dialogs/alerts,
  Cancel), content-based format detection (`unc_sniff` correctly
  identifies StuffIt), and — crucially — the **decompression engine
  itself**: in test-only mode (full decode + in-engine CRC
  verification, no disk writes) a real classic `.sit` reports
  "Extraction complete", proving the decoders produce correct output
  on a 68000. File creation and type/creator/date metadata
  (`PBSetCatInfo`) also work (the output file appears with the right
  Finder type/creator/date).

- **[SUPERSEDED — the whole of this bisection was confounded. See BLOCKERS.md
  "Earlier 'root causes' that turned out to be confounded": every File Manager
  open was silently failing throughout, so the observations below are real but
  the conclusions drawn from them are not. The write path works and is verified
  byte-exact on-Mac.]**
  Known bug — the disk-write path: enabling actual fork writes
  (`FSWrite`) triggers a layout-sensitive heap corruption, surfacing
  non-deterministically as a Sad Mac (dsMemFullErr=25 on a 4 MB
  machine — i.e. Memory-Manager-detected corruption, not real
  exhaustion) or an F-line bomb, or a spurious clean error. Ruled out
  by bisection: the engine decodes correctly (test-only clean); it is
  NOT an engine heap-block overrun (a tracked guard-byte allocator
  never tripped, matching the Linux ASan/UBSan cleanliness); NOT stack
  overflow (a 256 KB SetApplLimit bump did not help); NOT an FSWrite
  signature mismatch; and NOT floppy-specific (a 5 MB HD image crashes
  identically). Any NoteAlert or allocator-padding change masks it —
  the signature of memory corruption whose exact victim depends on
  heap layout. Root-causing further needs MacsBug (a Mac debugger);
  the heisenbug makes screenshot-driven bisection unreliable.

- **`FlushVol` after extraction** was added (durability: persist output
  before returning) — a genuine fix surfaced by the testing (writes
  were being lost on non-clean exit).

  not a fudge.** The autotest compares resource forks by CRC, and the System 6
  Resource Manager stamps session scratch into part of the header, so a raw CRC
  would mismatch every time. The masked range is exactly the 112-byte "reserved
  for system use" area of the 256-byte resource FILE header (Inside Macintosh:
  More Macintosh Toolbox, Resource Manager) — verified on a real fixture: `AT

## 2026-08-01 — testing a working directory without a Finder

`SFReply.vRefNum` with `dirID` 0 had been listed as untested since M10, and

the same directory — so none of them could have caught a mistake in this

## 2026-08-02 — driving the Mac OS 9 Finder with the keyboard, not the mouse

Getting the application to launch on Mac OS 9 took six boots. Five of them
were spent on the mouse.

The symptom never varied: the volume did not open. Three explanations were
published against it, each a real defect, each fixed, none of them the answer
— a double click spanning 0.9 s, an ADB pointer being fed absolute
coordinates, and the Setup Assistant holding the foreground. All three are
explanations of *clicking*, because the symptom was read as "the click was
wrong" rather than "something in the chain broke".

`tools/vmac/os9probe.py` broke the loop by measuring primitives instead of
outcomes, cheapest first, on targets that answer unambiguously: does a held
press pull a menu bar title down? does a single click merely SELECT the icon?
does the cursor go where it is sent? Eleven probes, one boot. Every mouse
probe changed exactly 0.0000 of its watched rectangle; every keyboard probe
worked; and the cursor-locating probe found the pointer only ever in screen
corners, never at any requested position.

So the decision is: **the Finder is driven from the keyboard.** Type to select
by name, Cmd-Down to open, Cmd-Q to quit. No coordinates to measure, no
double-click threshold to hit, nothing to re-measure when the desktop layout
changes. It worked first try and it is what `launch_by_keyboard()` does.

Two lessons, and the second is the one worth carrying:

- **Measure the primitive before theorising about the compound.** An outcome
  that did not happen names no link in the chain. This is the same mistake as
  the `macburger-helper.hqx` timeout, which was written up as an anomaly three
  times before anyone instrumented the byte counter.
- **A fix that is real is not thereby sufficient.** Three consecutive
  confirmed defects were fixed and the thing still did not work. Each fix felt
  like progress and each was published as a root cause. The habit that stops
  this is refusing to call anything a root cause until the symptom is gone.

## 2026-08-02 — checking Mac OS 9 output through the disk image, not the screen

Mini vMac's harness CRC-32s both forks on the Mac and paints the aggregate to
the framebuffer, because getting a floppy back out of Mini vMac mid-run is
awkward. That machinery — `at_report()`, the on-screen grid, `decode_grid.py`
— was the obvious thing to reuse on Mac OS 9, and it would have been the wrong
thing: it exists to work around a constraint OS 9 does not have.

The OS 9 transfer volume is a plain file on the host. So `verify_output()`
waits for the emulator to exit and then reads it: the Apple_HFS partition is
lifted out at the offset `mkapmdisk.py` wrote it at, hfsutils mounts it, and
`hcopy -m` pulls each extracted file off as MacBinary — which is how both
forks come across in one file, since hfsutils cannot copy a resource fork on
its own. The forks are then compared byte for byte with `unclassic x -nr`.

This is strictly stronger than the screen grid: it compares bytes rather than
a CRC of them, it needs no pixel decoding, it reports which file and which
fork differed, and it cannot be defeated by a 1bpp report routine meeting a
32-bit colour screen. It also answers a question nobody had asked — whether
the guest flushed its writes before being killed — because an unflushed volume
fails to mount or comes up a file short instead of passing quietly.

The general form: **when the environment changes, re-ask what the workaround
was working around.** The framebuffer channel was a good answer to Mini vMac's
constraint and a bad answer to QEMU's.

**It found a real bug within one run of being written**, which is the argument
for it. The on-screen grid reports `nfiles`, summed CRCs and summed lengths —
it has never compared a single output NAME, and could not, because a name does
not survive being summed into a CRC total. The first OS 9 sweep failed on
`synth-exo-Z.Z` and `synth-exo-gz.gz`: the Mac wrote `archive.sit~1` where
Linux wrote `archive`. Both fixtures are in `sample.txt` and both had been
passing on Mini vMac for weeks.

The cause was in the Mac shell, not the harness. `unclassic.h` documents
`name_hint` — the fallback name for formats that store none, gzip and .Z — as
"the archive filename minus its last extension"; `cli/main.c` strips the
extension, and `RunExtract()` passed the whole Pascal string. So opening
`foo.gz` on any Mac wrote a file called `foo.gz`, which collided with the
archive sitting beside it and became `foo.gz~1`, where every other
implementation writes `foo`. Fixed in `mac/unclassic_mac.c` with the same
rule the CLI uses, including "a leading dot is not an extension".

The lesson is about what a test is blind to rather than about the bug: **an
aggregate check cannot fail on a property it never aggregates.** Nobody had
written down that on-Mac names were unverified, because the harness looked
thorough — twelve formats, both forks, byte-exact. It was thorough about
bytes.

**And then the new checker's own first verdict was wrong, in the same shape.**
It reported 7/11, and all four failures were its blind spots rather than the
Mac's:

- it listed only the volume ROOT, so `synth-exo-tar.tar` — which extracts to
  `README.txt`, `bin/` and `docs/` — looked like one file of four, with the
  other three "MISSING". The Mac had written all four, correctly, in folders;
- it read HFS names as UTF-8. They are MacRoman, so PackIt's `Appé` compared
  unequal to itself. `run_diff.py` has decoded and NFC-normalized for exactly
  this reason for months;
- it treated "the Mac wrote nothing" as failure. For `derived-DandStoQIF2.sea`
  nothing is the CORRECT answer — the engine sniffs it as DiskDoubler, which
  is detect-only by the brief, and the app duly says "This file could not be
  extracted". Linux writes nothing either. Agreement on nothing is a pass, and
  it verifies the refusal path.

All three are fixed, and re-running the checker over the SAME captured volumes
turned 7/11 into 11/11 without the Mac doing anything differently — its output
never changed, only the reading of it. (Two further fixtures, a StuffIt 5 and
a 285 KB self-extracting archive, were added and run afterwards, for 13/13.)
The near-miss is the point
and is why it is written down: a FAIL from a young harness is a claim about
the harness until it is shown to be a claim about the target. That is the same
error as reading a cause into a timeout, arriving from the opposite direction.

## 2026-08-02 — the reporting channel, not the volume, was what blocked HFS+

"Extraction has never touched an HFS+ volume" sat in MANUAL_TESTS.md from M10
onwards, and it read like a missing capability: no HFS+ writer in this
environment, no way to prepare such a volume. It was not that at all.

The autotest build finds its volumes **by name** — `In` and `Out`. The Mac OS 9
boot volume is HFS+. Renaming it to `Out` in the Finder, from the keyboard,
points the existing binary at HFS+ with no code change whatsoever. The real
obstacle was in the other direction: `at_report()` writes 1bpp pixels straight
at the framebuffer, which is the best possible channel on a Mac Plus and
completely invisible on OS 9's 32-bit screen. The output volume was never the
problem. **The answer channel was**, and nothing had said so, because the row
was filed under what could not be written rather than what could not be read.

So `at_report_file()` writes the same values to a file on the plain-HFS INPUT
volume — the one the harness built, so the one it can always read, whatever
the volume under test happens to be. It carries every output NAME as well as
the aggregate, because an aggregate is precisely what cannot answer a question
about names, and names are most of what HFS+ might have changed.

Two things went the way this project keeps going, and both are worth keeping:

- **Two screen-based completion detectors were written before the artifact
  was.** First "wait for the screen to change", then "wait for it to go black,
  since at_report zeroes the framebuffer". Both ran to their full 240 s
  timeout on a run that had already succeeded — eight minutes of waiting for
  proxies that could not fire, on a run that takes two. Polling the host's
  copy of the transfer image for the report FILE finds it in ~20 s. **Wait for
  the artifact, not for a sign of the artifact.**
- **"It landed on HFS+" was nearly left as an inference.** The obvious check —
  ask the File Manager for the volume's signature — is worthless here: the
  classic API answers `'BD'` for an HFS+ volume for compatibility, so a
  negative proves nothing. The check that does work needs no guest code at
  all: hfsutils can see only the volume's HFS wrapper, so if the output were
  on plain HFS it would be visible there. It is not; the wrapper still holds
  its single placeholder file. A signature read at a fixed offset is exactly
  what produced the withdrawn "the boot volume is plain HFS" claim, so making
  the same read the basis of the fix would have been a poor joke.

## 2026-08-02 — the archive is no longer slurped into RAM

`RunExtract()` used to `NewPtr(fileSize)` and read the whole archive in before
the engine was given any budget. That cost landed entirely on the floor
target: on a 1 MB Mac Plus a 278 KB archive took 278 KB away from the engine
before extraction started, which is why README had to explain that *which*
StuffIt 5 entries fail there follows the size of the archive rather than what
is in it.

The justification, from M10, was that "interleaving File Manager reads of the
input with writes to output files on the same volume makes the input reads
return zeros". It was never reduced to a reproduction, and it was suspect for
a specific reason: **the very next bullet in the same list** — "deep writes
from the decode callback corrupt the HFS volume" — came from the same
investigation and had already been withdrawn, because it dates from the period
when every File Manager open was silently failing and it did not survive
re-testing. "Reads start returning zeros" is exactly what that confound looks
like.

`UNC_AT_INTERLEAVE` settles it. It reads one file three ways on one volume and
compares CRC-32s: undisturbed; in chunks with a fresh file created and written
on that same volume between every chunk; and again seeking explicitly with
`SetFPos` before every read, which is the shape a file-backed reader actually
has. **Identical every time** — 278,294 B / CRC 05746998 over 67 rounds, and
286,720 B / CRC 8f448a65 on a second fixture, at 4 MB and at 1 MB. The claim is
withdrawn.

So the default is now a `FileIO` that seeks and reads as the engine asks, with
the input file held open across the whole extraction. `UNC_MAC_SLURP_ARCHIVE`
keeps the old path buildable, the same way `UNC_MAC_STAGE_WRITES` keeps the
pre-streaming sink.

Measured on a real System 6.0.8 Mac Plus:

| run | before | after |
|---|---|---|
| 44-fixture sample, 4 MB | 44/44 | 44/44 |
| 44-fixture sample, **1 MB** | 39/44 | **40/44** |
| same sample, 4 MB, **output on the archive's own volume** | never run | **44/44** |

The 1 MB gain is one fixture, but the change under it is bigger than the tally
shows: three of the four that still fail went from refusing everything to
extracting most of it — `derived-Library_ISBN_Barcoder.sit` 0 of 34 entries to
**31 of 34**, `derived-Troi-ClipSave-Plug-in1.1.sit` 0 of 13 to **6 of 13**,
`derived-PuzzleGetter_0.8.sit` 11 of 26 to **25 of 26**. Each got back exactly
the budget its own archive had been occupying.

Two things worth keeping:

- **The same-volume case had never been tested at all.** Every autotest run in
  this project's history used a separate `In` and `Out` volume, while the
  interactive application writes next to the archive — one volume. That is
  precisely where the withdrawn claim lived, so the fix could not be trusted
  until it was covered: `UNC_AT_SAMEVOL` points the output at the input's
  volume and the read-back CRC does the rest. 44/44. **A harness can be
  thorough and still have never once assumed the shape the shipped program
  uses.**
- **A claim's neighbours are evidence about it.** This one sat directly beside
  a claim already withdrawn as confounded, in the same bullet list, from the
  same week. That was enough reason to re-test it, and it took one afternoon
  against a cost paid on every 1 MB extraction for months.

## 2026-08-02 — the Out volume can be read after all, so names are checkable

Three claims from the confounded period have now fallen in one day. This is
the third and the one that cost the most, because of what it forced rather
than what it broke.

BLOCKERS.md, under *test-harness lessons*:

> Mini vMac's disk write-back to the host image is lazy and PARTIAL — it can
> commit one fork of a file but not the other — so results cannot be read off
> the Out volume. Verification is done ON-SCREEN instead.

So the System 6 and 7 tiers verify through the framebuffer grid: a file count,
two summed CRC-32s, two summed lengths. That is a fine check of BYTES and
structurally incapable of checking a NAME, because a name does not survive
being summed into a CRC total. Which is exactly how the gzip/.Z fallback-name
defect — `foo.gz` extracting to `foo.gz~1` — sat in the corpus for weeks while
44 fixtures passed twice a day, until the Mac OS 9 harness read a directory
and saw it immediately.

It does not reproduce. `run.py --keep-disks` keeps each run's images and
`tools/vmac/checkdisk.py` reads them: **44/44 byte-exact, both forks, names and
folder structure included.** The decisive fixture is
`derived-RWAsm_Folder.sit` — 38 files and **73 forks**, dozens of them with
both forks non-empty, which is precisely the case the claim named as
impossible. An 8-bit folder name (`spinning brain ƒ`), a MacRoman `Appé` and a
`.DS_Store` all survive too.

The grid is kept. It is proven, it needs nothing of the volume, and it reports
liveness and setup failures that a disk cannot — `checkdisk.py` is an addition,
not a replacement. What changes is that the primary tier is no longer blind to
the one property the OS 9 tier had to catch for it.

**Its first verdict was 38/44, and all six failures were the checker's own.**
`hls` hides names beginning with a dot without `-a`; every hfsutils path
argument must be MacRoman bytes, not the UTF-8 subprocess encodes by default;
and `<X>.rsrc` is a sidecar only when `<X>` exists beside it, which
vmac_check.py documents and which this had to learn again. Fixed, and 44/44 on
the SAME captured images — the Mac's output never changed, only the reading of
it. That is the second time in one day a young harness's FAIL turned out to be
a claim about the harness; it is worth expecting.

The lesson underneath all three withdrawals is the same and is now well
evidenced: **a workaround outlives the claim that justified it, and takes the
capability it displaced with it.** Nobody re-examined the screen channel for
months because it worked. It was not wrong — it was unnecessarily blind, and
nothing recorded that difference until TESTING.md was made to say what each
layer cannot see.

## 2026-08-02 — the claim audit, finished

Every assertion this repository made about Mac or emulator behaviour without a
reproduction has now been tested. The list was short by the end, because most
had already been re-tested during the day:

|---|---|
| QuickDraw bombs after File Manager activity | withdrawn 2026-08-01 |

Two things are worth keeping out of it.

**Not everything was wrong.** `HideCursor()` is load-bearing, and the audit

asking first is not "is it true?" but "what does it stop us doing?".

## 2026-08-03 — the Arsenic block is grown, not assumed

StuffIt 5 was the one format the "runs on a Mac Plus" claim did not really
cover: 2 of 6 sampled fixtures extracted fully at 1 MB, three partially, one
not at all. Every write-up of it — including several of mine — described the
floor as hard, on the grounds that an Arsenic block is 512 KB and a 1 MB Mac
has about 700 KB of free heap, so there was nothing to win.

That reasoning was wrong in a way worth recording, because it was wrong about
which number mattered. **512 KB is what the block DECLARES, not what it
holds.** `blockbits` comes from the stream and every real Arsenic stream in the
corpus declares 512 KB, but the fill varies enormously: the fixture that peaked
at 643.2 KB on a 1 MB machine was a 512 KB allocation holding **24 KB**. The
transform vector has been sized to the actual fill since M9 for exactly this
reason; the block itself was still allocated at the declared size in
`ars_decode_init`, and nobody had asked why.

So `ars_block_reserve()` grows the block on demand, doubling from 8 KB, capped
at the declared size. Peak becomes `~35 KB parser + capacity + 4x fill`
instead of `~35 KB + 512 KB + 4x fill`. Measured on the corpus:

| fixture | before | after |
|---|---|---|
| `derived-RWAsm_Folder.sit` | 643 KB | **163 KB** |
| `derived-KeyGraphics.sit` | 656 KB | **176 KB** |
| `derived-PuzzleGetter_0.8.sit` | 710 KB | **262 KB** |
| `derived-Troi-ClipSave-Plug-in1.1.sit` | 1034 KB | **650 KB** |
| `derived-a2basic.dmg.sit` | 1319 KB | 1063 KB |
| `derived-Library_ISBN_Barcoder.sit` | 1810 KB | 1810 KB |

The last row is the shape of the result, not a failure of it: that fixture's
blocks really do hold ~316 KB, so doubling lands on 512 KB and nothing is
saved. The win is exactly proportional to how much of the declared block goes
unused, which is what it should be.

Two details that keep it honest:

- **Growing never sets the high-water mark.** During a growth both buffers are
  live, `old + new = 1.5x new`, and the later peak is `capacity + 4x fill`.
  Since 1.5x capacity < 5x fill for any fill worth having, the transient is
  never the peak — so the saving is real rather than moved.
- **The declared size is still enforced.** `blockbits` is 4 bits from the
  stream, so a block can legally declare as little as 512 bytes — smaller than
  the starting capacity — and the reserve clamps to it. The pre-existing
  corruption checks against `blocksize` are untouched; capacity is an
  allocation strategy, never a format bound.

The general form is one this repository keeps meeting from new angles: **a
number that comes from the data is not a number you have to budget for.** The
same mistake in the other direction — treating the archive's size as a cost the
engine must carry — was the RAM slurp removed the day before.

## 2026-08-03 — the LZW table is sized from the input, once

Same shape as the Arsenic block the entry above, found by looking for the same
shape: `unc_lzw_init` allocated `(1 << maxbits) * 4`, the **declared** ceiling.
`compress(1)` writes `maxbits=16` by default whatever it compressed, so `.Z`
cost a flat **274,432 B** for every input — a 488-byte fixture allocated 256 KB
for a table it filled a few hundred entries of. It was the second largest peak
in the format matrix and the only one that did not vary with its input at all,
which is what made it worth suspecting.

**Growth on demand was tried first, and was the wrong answer.** Doubling as
`ars_block_reserve` does measured:

    synth-exo-Z.Z          274,432 -> 18,432 B
    synth-exo-tar-Z.tar.Z  274,432 -> 61,440 B
    a2ps.V4.3.tar.Z        274,432 -> 208,896 B
    popper-1.7.tar.Z       274,432 -> 405,504 B      <- WORSE than doing nothing

That last row is the transferable part. Copy-based growth has an unavoidable
`old + new` transient, and **where the table IS the whole allocation, that
transient becomes the peak**. Arsenic escaped it only because its transform
vector is 4x the fill and dominates the later peak — the note above says as
much ("1.5x capacity < 5x fill"), and the condition simply does not hold here.
So the two cases look identical and are not: *growth pays off only when
something larger than the grown buffer is allocated after it.*

**What works is a bound from the input.** Every input code defines at most one
new symbol and codes are at least 9 bits wide, so

    symbols <= 256 + reserved + insize * 8 / 9

however large `maxbits` claims. One allocation, no transient, strictly smaller
than the ceiling in every case. `fmt_exo.c` passes the stream size less the
3-byte header; StuffIt method 2 passes the entry's compressed length.

The bound is **strict**, which is what lets the decode stay bit-identical:
reaching entry `256 + reserved + k` takes `k + 1` codes, so the table cannot
fill even when every code is the minimum width. That matters because
`maxsymbols` is not just an allocation size — it is where the code width stops
growing and where the table is declared full, both of which the encoder also
decided. Lowering it would silently desync the decoder from the encoder rather
than fail. So `maxsymbols` keeps its declared value and a new `capsymbols`
carries what is allocated; only `capsymbols` was substituted into the
allocation and the chain-buffer bound.

`lzw_grow` widens to the declared ceiling if the bound is ever under-estimated,
so a wrong estimate stays correct rather than overflowing. It is a safety net,
not a strategy, and **it was verified to be both**: with growth hard-disabled
the differential suite is still 769/769, so the bound never under-estimates
anywhere in the corpus; and with `-D UNC_LZW_TINY_TABLE`, which forces the
initial capacity to 258 so growth runs on every stream, it is *also* 769/769
under ASan/UBSan/alignment. Neither number means anything without the third:
starving the table without the safety net gives **675/769**, which is what
establishes that these fixtures can fail on this code at all. 94 of them
exercise it.

Result: zero regressions across the corpus, 50 fixtures improved, `.Z` down
from a flat 268 KB to 15–219 KB, and the 1 MB floor sweep unchanged at 41/44
(this was never what limited it). Numbers in FORMATS.md, footnote §.

## 2026-08-06 — method 13's LZSS window is sized from the entry

Third instance of the same shape, and the first where the ceiling is a genuine
format constant rather than a field read from the stream. `SIT13_WINDOW` is
64 KB because StuffIt method 13 says so, and that is correct — but it is the
size of the window the format PERMITS, not the size any given stream can
REACH. An offset is `pos - moff`, and a well-formed encoder never emits
`moff > pos`, because those bytes have not been produced yet. A fork whose
entire output is 6 KB can address 6 KB of window; the other 58 KB was
allocated, zeroed on every fork, and never read.

So the window is rounded up to a power of two at or above the fork's
uncompressed size, capped at 64 KB. The power of two is what keeps it exact:
with `win >= outlen`, `pos < outlen <= win`, so `pos & (win-1) == pos` and
`from & (win-1) == from` for every reachable offset — the same indices the
64 KB window computes, not merely equivalent ones.

**The assumption was measured, not argued.** `moff > pos` cannot happen in a
valid archive, but "cannot happen" is exactly the kind of claim this
repository has had to withdraw before, so an instrumented run counted them
across the whole corpus: **0**. That is a different check from the
differential suite passing — the suite would also pass if such references
existed and happened to read zeros either way.

Sensitivity was established the same way as the LZW bound: forcing the window
to its 256-byte minimum takes the suite to **654/769**, so 115 fixtures reach
this code and can fail on it. ASan stayed clean at that size too, which is
worth noting — the masking keeps every access in bounds even when the window
is wrong, so a bad bound here corrupts output rather than memory.

Result: 34 fixtures improved, none regressed, `derived-MacGzip.sit`
76,944 → 13,456 B. The corpus maximum is unchanged at 76,944 B because some
forks genuinely exceed 64 KB — this is a gain at the small end only.

**The estimate that motivated it was wrong, and the way it was wrong is the
lesson.** 175 of 225 StuffIt fixtures sat at exactly the 64 KB-window peak and
about two thirds had their largest fork under 64 KB, so ~115 fixtures looked
like they would improve. 34 did. The flaw: peak heap is the MAXIMUM over an
archive, so one fork over 64 KB anywhere pins the whole archive's peak at the
old figure, however many small forks it also has. **A per-archive maximum
cannot be predicted from a per-fork distribution** — the same class of error
as inferring Arsenic block sizes from peak heap (see the † footnote in
FORMATS.md), arrived at from the opposite direction.

## 2026-08-06 — the Arsenic block's first allocation is sized from the entry

Fourth in the "size it from the data" series, but the mechanism is different
and worth separating: this one was not about how MUCH was allocated. It was
about the shape left behind.

`ars_block_reserve` grew from 8 KB by doubling. For an entry whose block ends
at 128 KB that allocates 8, 16, 32, 64 and 128 KB, freeing each as it goes.
**A geometric trail can never satisfy the step that follows it** — the sum of
every earlier step is one step short — so the freed 8+16+32+64 KB sat under the
final block as 122,880 B of unusable holes. Measured on the 1 MB floor target
the stranded heap was 125,614 B, the rest being headers and small allocations.

That is what refused an entry in `derived-Troi-ClipSave-Plug-in1.1.sit`: its
transform vector asked for 498,548 B with 678 KB of budget still available and
`MaxBlock` at 468,126 B. The entry needed 666,004 B against a 678,392 B budget
— it was never short of memory, only of a contiguous run.

The fix is one line of sizing: the first allocation is
`min(outlen, blocksize)`. Both halves are bounds the data already gives —
a block cannot hold more than the entry's whole output, nor more than a block —
so there is normally no second allocation and no trail. Growth stays as a
safety net.

**It is a bound, not an exact size, and that cost 4 small regressions.** An
encoder may split a fork into several blocks even when `outlen < blocksize`, in
which case `outlen` over-allocates: `derived-Berkeley_Packet_Monitor.sit` went
338,964 → 362,236 B, and three others by 2 KB or less. Against that, 24
fixtures improved (`Library_ISBN` 1,854,208 → 1,682,080 B) and the floor target
went 41/44 → 42/44. The regressions were taken deliberately: none crosses the
400 KB budget threshold or the ~700 KB a 1 MB Mac has, so none costs a
capability, and the alternative sizings that avoid them all reintroduce a
trail. This is a weaker standard than the LZW change was held to, where any
regression was disqualifying, and the difference is that this one buys a
capability rather than an efficiency.

**How it was found is the transferable part.** Four configurations had already
been tried against this refusal and all four moved `MaxBlock` by under 500 B —
`NewPtr`, `MaxMem()` retry, handles with `MoveHHi`, and handles with the move
confirmed by address. Each assumed the LIVE blocks stranded the space. The
trail is made of DEAD ones, which no amount of moving the live blocks can
affect, and which nothing in the probe reported. The arithmetic that pointed at
it was simply noticing that 8+16+32+64 = 120 KB sat suspiciously close to the
125,614 B measured, and the confirming experiment was to set the initial
capacity to 128 KB so no growth happens at all — one build, one run, and the
fixture passed on the spot.

## 2026-08-07 — the inverse BWT falls back to a sampled occurrence index

Fifth and last in the "size it from the data" series, and the first one that
does not size anything: here the requirement itself is reduced.

`ars_inverse_bwt` builds a transform vector costing **4 bytes per block byte**,
and it is the dominant allocation in the decoder. OPEN_ITEMS.md had the
arithmetic: `Library_ISBN` needed 1,854,208 B against the 678,392 B a 1 MB Mac
Plus leaves the engine, of which 1,293,536 B was that one vector. No placement,
reserve tuning or defragmentation can close a gap that size — only needing less
can.

`ars_index_build` answers the same query from **samples**: the position of
every `1 << shift[c]`-th occurrence of each byte value, `shift[c]` chosen so no
value gets more than `target` samples. A query binary-searches the value that
owns the sorted index, jumps to the nearest sample and scans forward. Memory
`~4 * sum_c min(counts[c], target)`, time `~blocklen/target` positions scanned
per output byte — a pure time-for-memory dial.

**Samples are per byte VALUE, not per sorted index.** Per index looks more
natural and is worse: the scan then covers `target` occurrences of `c`, which
for a rare `c` is most of the block. Per value makes the scan `blocklen/target`
for every value, common or rare.

**It is adaptive, and the fast path is tried first at every block.** The choice
is made by an allocation failing, which is the only thing that knows the
caller's budget. Measured cost of carrying it on a machine that never needs it:
peak heap over all 31 StuffIt 5 fixtures is **HEAD + 8 bytes, exactly** — the
one pointer added to `struct Arsenic` — and the corpus is byte-exact.

**The dial is greedy, and that changes what "peak heap" means under a budget.**
`target` halves only until the allocator accepts, so the decoder takes the
largest index it can afford. Peak-under-budget is therefore roughly the budget,
not the requirement: `Library_ISBN` peaks at 614,080 B under a 678,392 B cap
but extracts fully down to **393,028 B** (bisected). Anyone comparing a
peak-under-budget figure against a predicted requirement is comparing two
different quantities — bisect for the requirement.

| fixture | needed before | predicted | measured minimum |
|---|---|---|---|
| `derived-a2basic.dmg.sit` | 1,088,588 | ~245,699 | **245,897** |
| `derived-Library_ISBN_Barcoder.sit` | 1,854,208 | ~379,435 | **393,028** |

**The prediction was good, and the last one was not — the difference is worth
keeping.** The method 13 LZSS estimate predicted ~115 improved fixtures and was
wrong, because peak heap is a per-archive MAXIMUM and it was estimated from a
per-fork distribution. This one was within 200 bytes on one fixture and 3.6% on
the other, because it estimated the size of a SINGLE allocation inside one
entry — exactly the quantity the change controls. **Estimate the thing you are
changing, not an aggregate over things you are not.**

**Time is the price, and it is uneven.** At the 1 MB budget the two floor
targets cost 2x and 3x (`a2basic` 20→50 ms, `Library_ISBN` 36→124 ms, x86 -O2).
The tail is worse: `derived-Domino_v1.4.sit` is 33x, because a tighter squeeze
picks a smaller `target`. The floor targets are the cheap ones, which is luck,
not design. At the extreme (`target=1`) the walk is quadratic: the whole
StuffIt 5 set takes 8.4 minutes instead of one second.

**On the target the price is 1.65x to 2.47x, and the x86 ratio does not
predict it.** Measured at authentic 7 MHz, both Arsenic fixtures, both paths:
`a2basic` 587 s fast / 966 s sampled (1.65x), `Library_ISBN` 768 s / 1,898 s
(2.47x). The ratio widens with block fill, as the `blocklen/target` model
says it should. The same `a2basic` ratio on x86 is 2.5x, so the fallback is
relatively *cheaper* on a 68000 — most likely because the arithmetic decoder
dominates more there and the BWT walk is a smaller share. The useful framing
is not "the fallback costs 65%" but "Arsenic already costs ten minutes on a
Plus, and this is what makes the entry extractable at all." Measuring it
needed a 1 MB 1x emulator that did not exist (`build_mv mv-1M-1x 1M z`); the
three builds `setup.sh` made were 4M/1M all-out and 4M-1x, and no all-out
build can answer a timing question.

Scaling one fixture by output size did not predict the other either:
`Library_ISBN` was called "near an hour" from `a2basic` and came in at 31.6
minutes. **Per-byte cost is not constant across fixtures**, for the same reason
the ratio is not — it tracks block fill.

**Degradation is bounded by an accident worth knowing about.** Squeezing the
budget below ~350 KB does not drive `target` to 1 and hang — it refuses the
BLOCK BUFFER first, and the entry fails cleanly. The block must be allocated
before the index is even planned, so the block is the binding constraint at
exactly the point where the index would become pathological. Probed from
678,392 B down to 200,000 B on `Library_ISBN`: clean `rc=0` to 450,000, 5 s at
400,000, clean per-entry refusal at and below 350,000, no hang at any point.
The robustness contract survives by construction rather than by a check.

**One thing the sampled walk breaks that the table did not: progress.** It
spends minutes turning input it has ALREADY consumed into output, so the
input-driven progress pump goes silent and a Mac user gets a frozen dialog and
a dead Cancel. `unc_progress_poll` fires the tick without moving the byte
count, called every `UNC_PROGRESS_STEP` output bytes and only on the sampled
path — the fast path never runs long enough to need it.

## 2026-08-07 — the progress dialog gets a bar, a percentage and a time left

The dialog had a Cancel button and a percentage rendered as text. Two things
made that inadequate once Arsenic became extractable on a 1 MB machine: a
15-minute extraction wants a time estimate, and — worse — the number it showed
was wrong for most of those fifteen minutes.

**The percentage was measuring the wrong thing, and the fix is in the engine,
not the UI.** Progress is counted in archive INPUT bytes consumed. Arsenic
decodes an entire block from the input and only then walks it into output, so
on a one-block fork the input position runs to the end while nothing has been
written, and then does not move at all for the whole walk. Measured on
`derived-a2basic.dmg.sit` under a 1 MB budget: 41 ticks, of which the last
**23 reported the identical value**. The bar would have sat at 100% for the
~42% of the run that the walk occupies — about seven minutes on a Mac Plus.

So the decoder now reports its own position instead of letting the input pump
do it. `UncProgressState.hold` suppresses the input-side tick for the duration
of the fork, and Arsenic reports `pbase + span * produced / outlen`, where
`span` is the fork's compressed length — already known, as `UncBufIn.limit`.
The unit the UI sees is unchanged (bytes of archive consumed) and the sequence
is monotonic; it is just interpolated across the fork by OUTPUT, which is what
the time is actually proportional to. After: 801 ticks, monotonic, evenly
spread.

**The tick interval is 256 output bytes, not the engine's 8192.** Arsenic's
bytes are expensive: at 8 KB the same run reports once every 37 seconds, which
is a bar that jumps in 4% steps and a Cancel button that takes half a minute to
answer. 256 gives ~1.2 s. The cost is a compare per output byte and a callback
the Mac shell rate-limits to 10 Hz; the 769-fixture suite runs in the same time
as before.

**The bar is a DITL userItem with a real draw proc**, not something painted
over the dialog, so it survives update events rather than relying on the next
tick to repair it. The ETA is `elapsed * (100 - pct) / pct`, held back for the
first two seconds and below 1% where it is meaningless, and both the bar and
the text are redrawn only when the displayed reading changes — at 10 Hz,
`SetDialogItemText` on every tick flickers.

**Moving the button broke the harness silently, which is the part worth
keeping.** The dialog grew from 80 to 110 points tall and Cancel moved down 30
with it. `interactive.py` clicks a hard-coded coordinate measured off an old
screenshot, so the click landed on inert dialog background: the extraction ran
happily to completion and the run still produced a `3-cancelled.png` — of the
progress dialog rather than the alert. Nothing failed. **A UI harness that
drives by coordinate cannot fail on a moved control; it can only produce a
screenshot of the wrong thing**, which is worthless unless somebody looks. The
constant now carries the arithmetic that derives it from the DLOG and DITL
rects, so the next person can recompute rather than re-measure.

## 2026-08-07 — the progress rewrite costs ~9% on a 68000, and why is UNKNOWN

Recorded as an observation, not a finding: the mechanism has no reproduction
and three plausible explanations have each been measured and killed.

**Measured, and reproducible.** `derived-a2basic.dmg.sit`, 4 MB Mac Plus at
authentic 7 MHz, extraction only, fast inverse BWT on both sides:

| build | 4 MB (fast table) | 1 MB (sampled index) |
|---|---|---|
| b4b5429 (before the progress rewrite) | 536 s, 537 s | 927 s |
| 8248ab8 (after) | 583 s, 587 s, 582 s | 966 s, 966 s |
| delta | **+47 s** | **+39 s** |

Host idle throughout (load 0.18, no stray emulators). Note the shape: the two
deltas are close in ABSOLUTE terms on the same fixture, not in percentage —
+47 s and +39 s for the same 205,019 bytes of output — so "9%" is the wrong
way to describe it. It is a cost of roughly 40 s attached to this fixture,
which reads as 9% of the fast path and 4% of the slow one.

**What it is NOT.** Each of these was a stated hypothesis, tested, and wrong:

- *The autotest grid.* `at_report` erases the whole 21,888-byte framebuffer a
  byte at a time and repaints 272 cells, and the rewrite took a2basic from 41
  reports to 801. Rate-limiting the grid to one repaint per 5 s (from 801 to
  ~117) changed the time by nothing: 587 s. The rate limit is kept anyway —
  the instrument should not scale with the thing it measures — but it is not
  the cause.
- *The tick rate, and therefore anything charged per tick.* Setting
  `ARS_PROGRESS_STEP` back to 8192, i.e. 26 progress calls instead of 801,
  also changed nothing: 582 s. This is the strongest constraint available: a
  30x reduction in callbacks bought zero, so whatever costs 40 s is not paid
  per callback. It also rules out `ars_scale`'s 32-bit divisions.
- *The engine change costing x86 time.* It does not. Ten runs of `unclassic t`
  on the same fixture: 19 ms before, 19 ms after.

**What it IS, as far as the evidence goes.** Copying only the four changed
`src/` files into the b4b5429 worktree, keeping its Mac shell, reproduces the
slowdown exactly: 582 s. So it is the engine diff, on a 68000, and not the Mac
shell and not the reporting. The only per-output-byte addition in that diff is
one `produced >= nexttick` compare over 205,019 iterations, which cannot
account for 50 seconds at 7.83 MHz — that would be ~1,900 cycles a byte. The
arithmetic is irreconcilable with the measurement, which is exactly why this
is written down as unexplained rather than attributed.

**It is being kept regardless, and that is a judgement, not an oversight.**
What the 9% buys is a progress bar that moves and a Cancel button that answers
in about a second instead of thirty-seven — on extractions that run for a
quarter of an hour. A user who cannot tell a working machine from a hung one,
and cannot stop it, is worse off than one who waits 9% longer.

**Anyone picking this up, in order of cost.** Do not re-test the four killed
hypotheses above.

1. *Is the cost fixed, or proportional to output?* Two runs of
   `derived-KeyGraphics.sit` (33 KB of output against a2basic's 205 KB), old
   build and new, four minutes total. A fixed ~40 s would dominate that
   fixture; a proportional cost would show ~7 s. This is the cheapest
   discriminator there is and it splits the remaining space in half.
2. *Is it the per-byte compare?* Keep `ps->hold` and `unc_progress_at`, delete
   only the `produced >= nexttick` test from the output loop and tick from
   `ars_read_block` instead. One 10-minute run.

The arithmetic says it cannot be the compare — 40 s over 205,019 iterations is
1,600 cycles a byte at 7.83 MHz — but the arithmetic also said it could not be
the reporting, and the measurement disagreed with that too. Measure before
believing either.

## 2026-08-07 — releases are published by Actions, not by a token here

The machine that develops this repository authenticates with a **deploy key**.
That signs git over SSH and cannot reach the Releases REST API at all, so v0.5
first shipped as committed files with no release page behind it.

Two ways out. Issue a personal access token to that machine, or let a workflow
do it with the runner's own `GITHUB_TOKEN`. **The workflow wins, and the reason
is not convenience:** a token stored here persists across sessions and grants
its whole scope to anything that runs, including a confused or compromised
agent session, whereas the workflow's credential exists for the length of one
run and is scoped to one repository by construction. It also keeps working
when nobody is at the keyboard, and leaves an audit trail in the Actions log.

`.github/workflows/release.yml` publishes what is committed in `dist/` rather
than building. Retro68 is a large cross-toolchain and `dist/` is committed
precisely so a person with an old Mac and no compiler can download the thing;
building it twice would only add a way for the two to disagree. The workflow
refuses to publish a missing or empty asset — a release with a broken download
is worse than no release, because it looks finished.

`gh` is preinstalled on GitHub-hosted runners, so no third-party action is
pinned here either.

**What this costs: nobody on this machine can confirm a release exists.** The
repo is private, the deploy key cannot read the Releases or Actions API, and
every unauthenticated call returns 404. Verification is a human step, and the
procedure in CLAUDE.md says so rather than letting a green `git push` be
mistaken for a published release.

Two assumptions were open when this was written and are now **confirmed by
v0.5**: a deploy-key push may add files under `.github/workflows/` (the
workflow-scope restriction applies to PATs over HTTPS, not SSH), and a
deploy-key tag push does trigger a workflow (the no-recursion rule applies to
`GITHUB_TOKEN`-driven events).

## 2026-08-08 — the undecidability was the oracle's fork convention, not the archives

Nine fixtures had no manifest and were recorded as ground truth the oracle
could not produce. Both reasons were properties of one flag, `unar -k visible`:

- Seven held an entry `X` and an entry `X.rsrc` (a THINK C project is exactly
  that shape). Under the `.rsrc` suffix convention one entry's sidecar is
  another entry's name, so the extraction tree cannot say which is which.
- Two had a leading `~` in a name. GNUstep's `stringByAppendingPathExtension:`
  refuses that, and unar then writes the AppleDouble container into the
  *data*-fork filename — sometimes without printing the warning the manifest
  builder guarded on.

`unar -k hidden` names the container `._NAME`. Prefixing never calls the path
code that fails, and the `._` namespace is disjoint from real archive names.
All nine build cleanly, and the differential suite goes 769 → 778.

**The manifest never encoded the convention** — it stores entry names and
per-fork hashes — so this changes the measuring apparatus, not the ground
truth. Rebuilding all 774 pre-existing manifests confirmed it: entry for
entry identical, only the recorded `oracle` string differs. The two
conventions agreed everywhere both could speak, and differed only where one
of them could not speak at all.

The CLI needed `--forks hidden` for the same reason: `unclassic` wrote
`NAME.rsrc` too, so the harness had been comparing two trees written in the
same ambiguous encoding — a mistake inside that encoding could cancel out
between them. The default stays `visible`, matching unar; the harnesses pass
the flag.

**Transferable: "structurally undecidable" was a claim about the tool's output
format, and it was applied to the data.** The archives always contained the
answer. `unar --help` documents the alternative, and TESTING.md quoted the
line that names it — the sentence describing the limitation sat one paragraph
from its own remedy, from M1 on 2026-07-23 until now. Before recording
something as impossible, check whether it is impossible *under a flag you
chose*.

Two things this does not reach. The Mac tiers still read `<X>.rsrc` sidecars
(`vmac_check.py`, `checkdisk.py`), so the nine cannot simply be added to the
on-Mac sample without teaching those readers the same lesson; nothing does
that today. And a CLI user who does not pass `--forks hidden` still gets the
silent clobber on a THINK C archive (OPEN_ITEMS.md).

**The trap on the way in.** Under `-k hidden` a resource-only entry produces
only `._X` and no data file, which reads exactly like a dropped data fork —
and one of the two `~` fixtures is that shape, so a careless reading would
have "confirmed" the very bug being escaped. It is an empty data fork:
`lsar` reports the single entry with `XADIsResourceFork: 1`, and the container
holds ids 9 and 2 only. Checked before believing, on all nine.

## 2026-08-08 — the CLI refuses to write over its own output

The `.rsrc` suffix convention could destroy a fork in silence. Entry `X`'s
sidecar and entry `X.rsrc`'s data fork are the same path, and `sink_open_fork`
just opened it `"wb"`, so the second entry truncated the first one's resource
fork. Measured on `derived-Unzip101.sit`: `Source/UnZip.π`'s 7,048 B resource
fork becomes a 0-byte file, exit status 0, nothing on stderr. That is what the
CLI did unconditionally until now, and what `--overwrite` still does.

Every output open now `stat()`s first and fails the entry when the path is
already there, with a message naming both ways out (`--forks hidden` to keep
both forks, `--overwrite` for the old behaviour). It is a per-entry error like
a CRC mismatch, so extraction continues and the exit status is nonzero.

**Refusing beats switching the default to `._NAME`.** The suffix form is what
unar writes and what every example in these docs shows; making resource forks
invisible dotfiles for every archive is a bigger change than an error on the
rare one. More to the point, an error can carry its own remedy and a changed
default cannot. It also covers more than the sidecar case: two entries with
identical names, and re-extracting into a directory that already holds output,
had the same shape and the same silence.

One exemption: the envelope being unwrapped. `unclassic x` writes an
intermediate file, recurses into it, and deletes it when the inner layer
succeeds — so that file exists while the inner layer is writing, and an inner
entry may legitimately carry its name. The sink holds a pointer to that path
and allows it (and its sidecar) through. The five unwrap chains in `ci.sh` are
what would catch this being wrong.

**Transferable: fixing the harness can hide the defect it was hiding.** The
day's earlier change made `run_diff.py` extract with `--forks hidden`, which is
correct and which also means the corpus no longer exercises the shipped default
at all. The OPEN_ITEMS entry recording that said "the harnesses pass the flag
and are unaffected" — true, and not a reason to leave it. `tests/run_collide.sh`
therefore extracts with the DEFAULT convention and asserts the refusal; it was
run against the pre-fix binary first and fails there, which is the only reason
to believe it passes now.

**What that test cannot see:** it pins one archive's shape (`X` plus a real
`X.rsrc`). No corpus fixture holds two entries with byte-identical names, so
that branch of the same check is exercised only by re-extraction, and a
collision against a pre-existing unrelated file is not distinguished from one
of our own — both refuse, which is the safe direction but not a diagnosis.

## 2026-08-08 — the Mac-side checkers stopped guessing at sidecars

The three host-side readers decided what was a resource fork by a heuristic on
`<X>.rsrc`: it was a sidecar for `<X>` when `<X>` existed beside it, and a real
entry otherwise. That cannot be right for an archive where both are real, which
is precisely the nine fixtures recovered earlier the same day, so they could
not be replayed on the Mac at all. All reference extractions now use
`--forks hidden` and pair `._X`; `aggregate_dir`, `checkdisk.py` and
`check_mac_sink.py` no longer infer anything.

**On a Mac there was never an ambiguity to resolve.** HFS keeps the resource
fork inside the file, so `X` and `X.rsrc` are two unrelated files there and
always were. Every version of this problem has been about how the HOST stages
its copy of the comparison — which is why the mock File Manager in
`tests/mac_sink_test.c` now writes `._X` too: a `.rsrc` suffix invented a
collision the real File Manager does not have, making the mock *less* faithful
to the thing it stands in for.

Measured after the change, on the enlarged 53-fixture sample: **53/53 at 4 MB
on System 6.0.8, 53/53 at the 1 MB floor, 53/53 on System 7.0.1**, and **53/53
read back off the Out volumes with names and folder structure included**
(`--keep-disks` + `checkdisk.py`). Two of the nine also run through the
qemu-m68k mock in `ci.sh`, so the Mac sink's own code meets a THINK C archive
on the target's endianness.

**Adding one fixture of a new SHAPE found three harness defects that no amount
of re-running the old list could.** All three had been unfailable rather than
passing:

- `check_mac_sink.py` compared UTF-8 manifest names against the raw MacRoman
  bytes on disk. Every fixture in that harness's list was ASCII, so nothing
  had ever differed. `UnZip.π` differed.
- The same checker gated each comparison on a fork's size, so an entry with an
  empty data fork was never looked for at all. It now asserts presence
  whatever the size — a missing empty file is a real defect.
- `checkdisk.py` joined Mac path components with `/`, and `/` is a legal
  character in an HFS filename: `derived-unshar_1.11_folder.sit` holds
  `mw/68k•unshar π`. Two of its entries could not even be copied off the
  volume. Paths are tuples of components now, joined with `:` only when a
  Mac path is actually needed.

That last one is the same mistake as the `.rsrc` sidecar, one layer down: a
separator that is also legal inside a name. **The list a harness runs on is
part of the harness**, and a corpus that never contains the awkward shape
cannot report that the harness would mishandle it.

**The heuristic itself was in four readers.** `vmac_check.py`,
`checkdisk.py`, `os9.py` and `check_mac_sink.py` each had their own copy of
"a `<X>.rsrc` is a sidecar only when `<X>` is beside it", and one of the
comments said so out loud — *"vmac_check.py makes the same distinction for the
same reason"*. Fixing three of them left the fourth silently comparing against
a tree that no longer used that convention; the Mac OS 9 pair was found by
grepping for `.rsrc`, not by anything failing, because no CI job reaches that
tier. **One home per finding applies to code, not just to documents** — a
duplicated rule has to be re-found once per copy, and the copy nobody has a
test for is the one that survives.

## 2026-08-08 — "the oracle cannot read it" was the harness throwing evidence away

**Claim.** StuffIt method 1 (RLE90) had no oracle coverage because `unar`
fails on `derived-New_Python.sit`, the corpus's only method-1 fixture, so
`make_manifests.py` refused a manifest. Filed under *Loose ends* in
OPEN_ITEMS.md as needing "a method-1 archive `unar` can read".

**Evidence that it was wrong.** `unar` reads the method-1 fork perfectly. It
is the 470-byte resource fork of `I Want To Buy Some Cheese` (`rmeth=1`,
470 → 389), and it comes out byte-identical to ours. What `unar` fails on is
the *data* fork of a different entry, `It's A Bit Runny Sir`, compressed with
method **3**. Nine of that archive's ten forks were adjudicated ground truth
and all nine were being discarded to avoid recording the tenth.

**Consequence.** Manifests are now built per entry rather than per archive.
A fork the oracle failed on is recorded as `"unadjudicated": {fork: reason}`
with its hash omitted; everything else in the archive is ground truth as
usual. 19 fixtures that contributed nothing now contribute: the suite goes
778 → 793, and method 1 is oracle-adjudicated. Sabotaging `sit_rle90`'s run
length fails exactly one fixture, `derived-New_Python.sit` — the coverage is
real, and it was demonstrated failing before it was believed passing.

Four things here transfer:

- **The all-or-nothing rule was invisible because it never failed.**
  `oracle FAILED on X` scrolled past on every rebuild and read as a property
  of the fixture. It was a property of the *builder*: one bad fork vetoed
  nine good ones. A harness that discards evidence looks identical to a
  harness that never had it.
- **A true statement about the failure was applied to the wrong entry.**
  "unar fails on derived-New_Python.sit" is true, and the inference "so it
  cannot adjudicate method 1" does not follow — different entry, different
  method. The same shape as the 512 KB Arsenic claim: a fact about the
  archive used as a fact about the fork in front of you.
- **What a failed extraction leaves on disk is not one thing.** Three
  behaviours in 19 fixtures: a 0-byte file (most), 114,644 bytes of partial
  output (`guysmaccontacts.sea`), and a sidecar padded to the DECLARED length
  with garbage (`appledraw51.cpt`, whose 13,121 B disagrees with our 13,036).
  A first draft of this change cross-checked the parse by requiring failed
  forks to be empty on disk; two of the three shapes would have sailed
  through, and the padded sidecar would have become "ground truth". The parse
  is instead checked against unar's own failure count and against `lsar`'s
  independent entry list.
- **An excuse must be anchored to the other implementation, not to ours.**
  A per-entry error from `unclassic` is tolerated only where the oracle
  failed that same entry — a condition our code cannot influence. Tolerating
  "recognized but unsupported" in general would have been far easier and
  would have silently excused every StuffIt fixture the day someone broke the
  method dispatch table.

**And a fixture for what one real fork cannot reach.** `tools/synth_sit1.py`
generates `synth-sit-rle90.sit` (deterministic; container layout from the
same XADStuffItParser.m offsets the parser cites, RLE90 as the inverse of
XADRLE90Handle.m, with a self-test asserting the encoder really is that
inverse). The real fork exercises 25 run escapes and one literal `0x90`; the
synthetic one adds runs *of* `0x90`, the maximum 255-byte token, multi-token
runs, output ending inside a run, and the shortest legal token. Both forks of
every entry are method 1, since the real fixture only has it on the resource
side. Worth the file: breaking only the `c == 255` case fails
`synth-sit-rle90.sit` and **nothing else among the 225 StuffIt fixtures**,
which is every fixture that reaches `sit_rle90` at all.

## 2026-08-08 — a second oracle: `macunpack` adjudicates what `unar` cannot

**Claim.** "There is no oracle to check a method-6 implementation against."
**Evidence against.** `reference/macutils/macunpack/sit.c` has decoded StuffIt
fixed Huffman since 1991, and it was already sitting in this repository —
fetched by `tools/fetch_references.sh`, cited by other decoders here.
**Consequence.** `tools/build_macunpack.sh` builds it out of a copy of the
read-only reference tree, and `make_manifests.py` offers it every fork `unar`
left unadjudicated. 23 forks across 9 fixtures gained ground truth, the
differential suite went 793 → 795 fixtures, and the *only* forks now
unadjudicated in the run are ones our engine also declines.

Only 1 of those 23 forks is method 6. The other 22 are methods we already
implemented, on archives where `unar` happens to fail — so the value of a
second oracle had nothing to do with the feature that motivated it.

Three things transfer:

- **"No oracle exists" is a statement about one tool.** XADMaster refuses
  method 6; that is a fact about XADMaster. The generalisation to "the format
  cannot be adjudicated here" was never true, and it sat in three status files
  for a week. When a limitation names an implementation, read it as naming
  only that implementation.
- **A build flag can silently delete the branch you are testing.** macunpack
  must be built `-m32`: `util.c`'s `get4()` returns `unsigned long` and
  `sit.c` assigns it to a `long`, so the sign test that selects a *stored*
  method-6 segment is unreachable when `long` is 64 bits. Built LP64 it dies
  with "Premature EOF" on exactly the branch the synthetic fixture exists to
  adjudicate — an oracle that fails is at least loud, but one that fails
  *only* on your new code path looks like your bug.
- **A predicted output filename is a guess, and a guess becomes ground
  truth.** macunpack names files through `transname.c` (many-to-one) and
  writes nothing at all for an empty fork, so a mispredicted name is
  indistinguishable from an entry with two empty forks — and would have been
  recorded as a manifest saying so. The builder now refuses unless the
  `.info` file macunpack writes for every entry it extracted is present, and
  refuses any name two entries share. The rule is a condition, not a list of
  fixtures.

## 2026-08-08 — StuffIt method 6: the tree is generated, not built

Method 6 codes each segment with a Huffman tree whose SHAPE is a constant of
the format — macunpack derives it per fork from a fixed weight table
(`code6[258]`) by recursively splitting the leaf range at half the remaining
weight (`sit_dosplit`); only the byte each leaf stands for is declared per
segment, which is what "fixed" means. So the shape depends on nothing but a
constant, and `tools/gen_sit6_tables.py` computes it once into
`src/sit6_tables.h`: 514 nodes, depth 13, two `uint16_t` tables with the leaf
rows dropped. The engine walks it and never builds it.

That buys three things a per-fork build would not: no recursion (a rule here),
no 68000 cycles spent recomputing a constant for every fork of every archive,
and a generator that can afford to check itself — it asserts the result is a
tree, that all 258 leaves are reachable exactly once, and that no internal
node dangles, because *a tree that agrees only with itself proves nothing*.

The segment buffer is freed and reallocated when a segment needs it bigger,
never grown by copying. At a segment boundary the old contents are dead, so
copy-based growth would pay an `old + new` transient for bytes nobody reads —
which is what made growth-on-demand lose to one-shot sizing for the LZW table
(2026-08-03, above). Same shape, opposite answer, for the same reason: what
matters is whether the old bytes are still needed.

**And a fixture for what one real fork cannot reach.** The corpus's single
method-6 fork (34,818 B, `derived-INITLoader.sit`) is two Huffman-coded
segments, so it never takes the *stored* branch and never sees a `0x80`
PackBits filler, the shortest run, or a fork of more than two segments.
`tools/synth_sit6.py` generates `synth-sit-fixhuf.sit` — deterministic, five
entries, both forks method 6, ten forks in all — covering the stored branch,
both segment orders, every PackBits control-byte edge, a one-byte alphabet and
a 254-byte one, and twelve segments in one fork. It reads the code tree out of
the generated header rather than reimplementing it, and self-tests by decoding
its own output the way `sit_fixhuf` does. The oracle for it is macunpack, and
all ten forks are byte-exact against it — including the stored branch, which
is the one an LP64 oracle cannot see.

## 2026-08-08 — an excuse must be anchored outside our own output

Reviewing the per-entry oracle work of earlier the same day turned up no
hardcoded fixture names — discovery really is by condition throughout — but
two excuses that could not fail, and both were found by asking the same
question: *what evidence does this tolerance rest on?*

**The first rested on our own error message.** `run_diff.py` skipped a whole
fixture when every entry our binary reported failed with "recognized but
unsupported". So the thing being graded decided whether it was graded. Two
costs, both measured:

- `4acalc.zip` and `4alnch11.zip` carry adjudicated hashes for 5 of their 7
  entries, because `unar` implements Implode and we do not. Ten forks, plus
  their names and entry counts, were never compared. The reason on record —
  "even unar fails on them" (DECISIONS.md, M8) — had been false since
  per-entry manifests landed that morning, and the disproof was in the
  manifests themselves. **Two files disagreeing, again**: the third time that
  mechanism has produced a finding here.
- a regression that made a SUPPORTED method report "recognized but
  unsupported" for a whole archive turned a failure into a skip. The
  mitigation on record was a printed count for a human to compare against a
  number in TESTING.md — and that number silently went 3 → 2 earlier the same
  day when method 6 landed, which is exactly the change it was supposed to
  make visible.

The fix is to anchor the excuse in the ORACLE: `lsar` already names every
entry's compression method, so manifests now record `oracle_methods` and the
harness excuses "recognized but unsupported" only where the oracle says the
method is outside v1 scope (`ORACLE_OUT_OF_SCOPE`, today just `Implode`). No
fixture is skipped for anything our binary says any more; an out-of-scope
entry is still graded on its name, on its entry count, and on anything the
engine did write, so implementing Implode starts ten comparisons with no
change to the harness. The set deliberately lists only methods the corpus
contains: an unlisted one fails the suite loudly, where a misspelled guess
would excuse nothing silently.

**The second rested on the oracle, but too coarsely.** Where the oracle had
failed ONE fork of an entry, our engine's absence was excused for the whole
entry — so a fork with ground truth sitting beside an unadjudicated one was
never required to exist. Six fixtures are shaped like that. Absence is now
excused only for out-of-scope entries; an adjudicated fork is compared or
reported missing.

**Both were demonstrated failing before they were called fixed**, with stub
binaries rather than a sabotaged engine: one that writes nothing for
`•Draw 5.1.cpt` (78,123 B of adjudicated data fork) and one that calls every
entry of the fully-adjudicated `derived-Export.sit` unsupported. Both passed
before, both fail now, and the real engine's results did not move — 795 → 797
fixtures graded, because the two zips stopped being skipped.

**Also guarded: a many-to-one match key that trusted uniqueness.**
`matchkey()` flattens `:` and `/` to `_` so unar's progress report can be
matched against paths on disk. Two different entry names can therefore share a
key, and the failure would be attributed to whichever the walk reached first —
leaving the entry that really failed holding hashes of whatever unar dropped
on disk, which the same day's notes record can be a sidecar padded with
garbage. No fixture in the corpus collides; the builder now refuses one that
does, the way the macunpack matcher already refused its own collisions. **Two
matchers in one file disagreeing about the same hazard is a bug even when
neither has fired.**

## 2026-08-08 — Multi-segment archives: one scheme, chosen for its header

Multi-segment moved from "out of scope (v1)" to in scope. One scheme is
implemented as a proof of concept and the rest are filed in OPEN_ITEMS.md.

**Which scheme, and why it was not a toss-up.** The candidates were
StuffIt segments, Compact Pro segmented archives, spanned Zip
(`.z01`/`.zip`), and a plain `.001` split. The requirement — parts that
may be anywhere and named anything — is decidable only where a part
says what it is:

| scheme | what identifies a part | oracle here |
|---|---|---|
| StuffIt segments | 100-byte header: part number, original name, 26 fingerprint bytes | `unar` |
| Compact Pro segmented | a volume byte per archive and per entry; segment 2+ layout undocumented | **none** — neither `unar` nor `macunpack` extracts them |
| spanned Zip | the filename extension* | `unar` |
| `.001` split | the filename, and nothing else | `unar`, only when part 1 is not itself a recognizable archive |

\* Too coarse, corrected 2026-08-09 when the scheme was implemented:
its first and last parts DO identify themselves, and the last is the
only place the part count is written. See the entry of that date.

A `.001` split would have been the least code and cannot meet the
brief at all: with no header, the name is the only evidence there is.
Compact Pro is the one classic-Mac scheme with no reference
implementation to transcribe or check against, so it needs a genuine
sample before a line is written. StuffIt segments is both the cheapest
and the strongest, and its join touches no decoder: the payload is a
byte concatenation, so this is an envelope in the shape of MacBinary.

**The engine sequences, the host opens.** Parts arrive through an
`UncVolumeSource` callback, so no file is touched from the engine, the
joiner is a caller-provided struct (no allocation), and the "where is
part 2?" question lands where it belongs — a directory scan in the CLI,
an alert in the Mac shell. The joiner keeps **one part open at a time**:
a Mac Plus with one floppy drive cannot mount two, and System 6 counts
its FCBs.

**Two things the header gives away, both load-bearing.** `rsrclen +
datalen` is the exact payload total, so a set is known to be complete
without a part count — and none is stored in the format, which is also
why XADMaster stops at the first gap rather than knowing when to stop.
And a set of one part is an ordinary file with a 100-byte hat, so it
extracts with no volume source at all.

**A missing part is the archive's verdict, not the entry's.** The
joiner reports an unavailable part as EOF, so the entry ends as a
per-entry `UNC_ERR_TRUNCATED` with its partial output kept and the sink
told, while the call returns `UNC_ERR_SEGMENTED` — the first code path
in the project that ever produces that error, which had been declared
in `unclassic.h` since M0 and returned by nothing.

**Backward crossings are measured, not assumed.** A backward seek
across a part boundary re-opens a part, which on removable media is a
disk the user has to put back. `unc_segment_stats()` counts them and
`--stats` prints them: **0 on both the 3-part and 12-part cases.** The
StuffIt join is read strictly forward, so the swap-thrash problem this
design was braced for does not exist for this scheme. It is reported
per run rather than concluded once, because it is a property of the
container inside the join, not of the joiner.

### The oracle's discovery is name-gated; ours is not

`unar` matches parts by content — but only among files whose name
starts with the opened part's basename. Renaming the parts of a valid
set makes it disappear from the oracle entirely. That is not a bug we
inherit: our discovery reads every file in the folder and asks the
engine. It does mean the `misnamed` case cannot be adjudicated in
place, so it is adjudicated on a renamed copy of the same bytes — the
payload stays oracle-checked, and what the case tests is discovery.

**And the trap that would have poisoned the ground truth:** `unar
Part.1` joins nothing and extracts part 1 alone, looking entirely
successful, while `unar ./Part.1` works. `[name
stringByDeletingLastPathComponent]` returns `@""` for a bare relative
name, and the `if(!dirname) dirname=@"."` guard tests for nil, not
emptiness. A manifest built that way would have been truncated, and our
correct output would have "failed" against it. Reproduced, cause read
in the reference source, and written down where the next harness author
will look (TESTING.md).

## 2026-08-09 — Asking where the output goes, on a system with no folder picker

Output went beside the archive, which is right on a hard disk and wrong
on floppies: the volume holding the output is the volume that has to be
ejected to insert the next part. OPEN_ITEMS.md had it filed as "needs a
destination picker, which is a UI change beyond the alert".

**There is no folder picker to call.** `CustomGetFile` and its hooks
arrive with System 7 and the floor target is System 6.0.x, so the
classic idiom is `SFPutFile`: take the *location* out of the reply and
ignore the name. That is what the application now does between
`SFGetFile` and the extraction.

**Why it does not change what anyone had.** Standard File keeps ONE
current folder across `SFGetFile` and `SFPutFile`, so the destination
dialog opens in the folder the archive was just chosen from and Return
means "beside the archive" — the previous behaviour, reachable without
reading anything. Navigating is the addition, not the default.

**Two traps, both photographed rather than reasoned about.**

Standard File's prompt is one static text item about 200 points wide
and it does not wrap. "Extract the files into this folder:" rendered on
System 6 as "Extract the files into this" — the word carrying the
meaning was the word that fell off. It is now "Extract into this
folder:". A prompt is a fixed-width resource, not a sentence.

And the name in the box was seeded with `reply.fName`, which is the
archive's own name in the archive's own folder, so pressing Save raised
**"Replace existing "archive.sit"?"** — on the DEFAULT path, the one
that means "beside the archive". Nothing is written under that name
whichever button is pressed, because the name is ignored; the alert
simply asks the user to overwrite the file they just opened, and its
default button is No, which returns to the dialog. The default name is
a constant now.

**And they look far too alike.** Two Standard File boxes at the same
spot, same list, same Eject and Drive; the second differs by a prompt
line, a name box and Save where Open was. A reader not looking for
those reads it as the first dialog redrawn — which is how it was
reported here.

**The open dialog cannot be labelled through `SFGetFile`.** Its `prompt`
argument is documented "Ignored", for `SFGetFile` and `SFPGetFile`
alike (Inside Macintosh: Files, Standard File Package). That was
confirmed here before the documentation was found: "Open an archive:"
was passed and photographed on System 6.0.8, and the frame came back
pixel-for-pixel identical to the empty-prompt one — 0 of 175,104
differing.

**There IS a placeholder in the item list, and it is parked.** `DITL`
-4000 was read out of the System file's own resource fork (`hcopy -m`
the System off the image, walk the resource map; the parser was
cross-checked by reproducing our `DITL` 128 item for item against
`mac/unclassic.r`). Ten items, of which item 10 is an *enabled*
`statText` with empty text at rect t=1044 l=20 b=1145 r=116 — a
thousand points below a dialog that is 348x200. Item 2, a button, is
parked the same way at t=1152. So the empty text item exists; nothing
draws it, and it is nowhere near the white band at the top. Apple
documents the customization route as `SFPGetFile` with "the resource ID
of a **customized** dialog template", so dragging that item into view
under the STANDARD template is undocumented behaviour and not something
to build on.

**The white band is layout, not a placeholder**, which the same dump
settles: the open dialog's first visible item starts at t=39 and the
save dialog's at t=29. Ten points — exactly the 21-against-11 measured
on screen between each frame's border and its volume box.

So the cue is POSITION: the destination dialog opens 30 points down and
right, and visibly moves. Sizes measured for the offset — open 366x216,
destination 322x200 — so both still sit whole on a 512x342 screen.

**The bug was reachable only where nothing was looking.** The phase
written to test the feature switches the destination to an EMPTY floppy,
where the archive's name collides with nothing — so `--dest` passed,
twice, while the case every other phase exercises was broken. A test
aimed at the new path can leave the default path less covered than it
was before the change.

**And the phases that did hit it reported success.** The default
interactive phase spent its entire run in that alert and printed
"extraction settled after ~134s"; `settle` cannot tell a static alert
from a static result, and that phase is photograph-only by design
(tools/vmac/README.md). It was found by looking at the frames, which is
the one step that is written down as mandatory and is the easiest to
skip.

### A "the screen stopped changing" oracle is a "the screen is changing slowly" oracle

`interactive.py --dest` asserts on the volumes rather than on a
screenshot, because "Extraction complete." looks identical wherever the
bytes went. Its first run reported the output on the WRONG volume, and
the application was right: `Mac.settle` had returned while the progress
dialog read 33%, and the phase then read a half-written floppy.

`settle` polls for two consecutive identical frames. The progress
dialog repaints once per engine callback — every 8–16 KB of *input* —
so on a slow decode consecutive polls land inside one gap and a running
extraction is indistinguishable from a finished one. The fix is not a
bigger poll interval but a different question: `quiet=EXTRACT_QUIET`
asks for a number of SECONDS the screen must hold still, and that
number has to exceed the worst repaint gap. Every settle waiting on an
extraction now passes it; the ones waiting on a boot do not need it,
because what precedes a booted screen is continuous repainting.

Two things worth carrying:

- **The unsound wait had been in every interactive phase since M10 and
  had never failed**, because those phases extract to a hard disk and
  judge the result by eye. It took an assertion — one that can fail —
  to expose it, and it failed in the direction that accuses the
  application. That is the third time in two days that a UI harness's
  own defect arrived dressed as an application bug (the other two are
  in the entry above).
- **The readback was a second copy of a solved problem.** It listed the
  volume with `hls -1` split on whitespace, so "Demo Manual V1.6" was
  three names and no fixture with a space in an entry name could ever
  pass; `checkdisk.walk` had handled that, plus dot-files, folders and
  `/` inside an HFS name, since 2026-08-08. It is imported now. A
  harness that re-derives a name rule gets the old version of it.

## 2026-08-09 — Reacting to the disk going in, and three wrong diagnoses

OPEN_ITEMS.md held this back deliberately: "so that the shipped code has
no path that nothing exercises". The gate was testability, and the
escape clause was a claim — "Mini vMac mounts an image mid-run" — so the
claim was tested first. It is true, and it needed a tool: Mini vMac's
X11 build takes a runtime disk through **XDND only** (control mode
offers magnify, reset, interrupt, quit and speed, no open-disk; the
build sets `NeedRequestInsertDisk 0`), and `ParseOneUri` turns a `file:`
URI into `Sony_Insert1a`. With no window manager or file manager on the
harness display there was nothing to drag from, so
`tools/vmac/xdnd_insert.c` is the missing drag source. Proven before any
application code was written: one volume and a dimmed Drive button
before the drop, `LateDisk` in Standard File after it.

The feature itself is an alert filter that scans the newly mounted
volume and takes the alert down when the wanted part is on it. What it
cost was three diagnoses, each wrong, each a run:

- **A modal filter never sees a disk-inserted event.** `ModalDialog`
  "calls the Event Manager function GetNextEvent with a mask that
  excludes disk-inserted events" (Inside Macintosh: Toolbox Essentials).
  Found by building a version that dismissed the alert on ANY `diskEvt`
  reaching the filter; it sat through two insertions unmoved. The queue
  has to be read directly.
- **Fetching the event is also what mounts the disk.** After the fetch
  broke something else, it was replaced by a polite version that touched
  no events and polled the volume list twice a second — which never saw
  a volume appear at all. The mount result is what the event's high word
  carries; until somebody fetches it, nothing has mounted.
- **Supplying a filter replaces the standard one, and with it the
  default button.** This is what actually broke `--segments`, three runs
  running, while the blame went to volume selection and then to event
  consumption. An alert with no filter gets a standard filter that maps
  Return and Enter to item 1; ours took that away, so the alert ignored
  its own default button and every later step of the phase clicked into
  a dialog that should have closed. The filter now handles Return itself.

Also true, and nearly missed: the filter is **throttled to twice a
second**, because calling `GetNextEvent` on every pass takes events out
from under the loop that owns them.

**The lesson is about method, not about dialogs.** Three explanations
were produced and two were confidently wrong, each costing an emulator
run, because each was reasoned from a failing tally. What ended it was
one screenshot taken at the moment in question — the alert still on
screen three seconds after Return — which named the cause immediately.
When a symptom is "the sequence went wrong somewhere", photograph the
step rather than theorise about the outcome.

`PostEvent` is declared by this toolchain and not implemented; a design
that leaned on putting an event back died at the linker, which was the
cheapest of the four failures.

## 2026-08-09 — Spanned zip: the second scheme, and what it cannot promise

M11 shipped with one segmentation scheme and a table ranking the rest by
"what identifies a part". Spanned Zip was second, its answer recorded as
"the filename extension". That answer was too coarse, and getting it
right is most of this entry.

**A spanned zip identifies two of its parts and no others.** The first
carries a local file header displaced to offset 4 (XADZipParser.m
`+recognizeFileWithHandle:`). The last carries the end-of-central-directory
record, which is the ONE place the part count is written. Everything
between them is undistinguished archive data — no marker, no index, no
number. `unar` refuses such a part too, and the suite asserts that it
does, so the premise is re-checked on every run rather than quoted from
this entry.

That asymmetry decides the whole design. Discovery cannot start from the
part the user opened, the way the StuffIt scheme does: it has to reach
the LAST part first, because nothing else knows how many there are. So
the CLI resolves any member of a `NAME.zNN` / `NAME.zip` family to the
`.zip` (the volume regex in XADZipParser.m `+volumesForHandle:`, matched
case-insensitively), describes that, and only then knows what to ask for.

**Names propose; content disposes.** Ordering parts by filename is
evidence of nothing, and this project's stated bar is that a part be
identifiable from its own bytes. A spanned zip cannot meet it — but it
can be made to prove itself *afterwards*, which is nearly as good and is
the honest version of the claim. The assembled stream is required to
agree with itself in three places: the part count must match the one the
EOCD states, the central directory must begin where that record says it
does, and every entry's local header must be found at the offset the
directory gives for it, with its CRC-32 checked as always. So the API
promise is not "a wrong part is refused" but "a wrong part cannot pass
silently", and the two are different sentences.

Which is worth nothing unless the checks are load-bearing, so that was
measured rather than asserted. Building a deliberately lax reader — CRC
comparison removed, local-header signature check removed — and running
the suite makes exactly two cases fail: *parts in the wrong order
extracted cleanly* and *a foreign part extracted cleanly*. Those two
assertions are the ones holding the scheme up, and they are not vacuous.

**A producer's marker records how a file was made, not what it is.**
`zip -s` writes `50 4B 07 08` in front of the first part. It also writes
it when the archive did not need splitting at all: the result is one
file, its EOCD says "disk 0", and nothing is missing. Reading that marker
as "this is a segment" would refuse a file that extracts perfectly.
Deciding it the other way round — the EOCD is the authority, the marker
is only a shape — turned up a gap that predates this work: such an
archive sniffed as *unknown* and could not be extracted at all, because
`unc_zip_probe` looked for a local header only at offset 0. Accepting one
at offset 4 (the reference's own rule) fixes it, and cost nothing: across
1,609 corpus files, zero have those bytes there and no fixture changes
what it sniffs as.

**"0 backward crossings" is a fact about StuffIt's layout, not about
joining.** The M11 entry above reports it as a measured property and
braced for swap-thrash that did not materialise. It does materialise
here — but only ONE crossing of it is the format's doing, and the rest
is this implementation's. Part opens (backward), measured on the
suite's cases beside the floor computed from each archive's own
directory:

| case | parts | first version | now = floor |
|---|---|---|---|
| `zstored` | 5 | 22 (7 back) | **6 (1 back)** |
| `zdeflate` | 4 | 18 (6) | **5 (1)** |
| `znested` | 3 | 14 (5) | **4 (1)** |
| `zmany` | 12 | 49 (14) | **14 (2)** |
| StuffIt `many12`, for contrast | 12 | 12 (0) | 12 (0) |

`zmany`'s floor is 2 backward crossings, not 1, because its central
directory begins on part 11 and crosses into part 12: where the
directory *sits* is part of the floor, and the first version of the
model left that out and accused the reader of two opens it had no way
to avoid. **A floor that is too low is not a safe error** — it reads as
a defect in the thing being measured. `run_segments.py` now computes
the floor from each archive's own directory and requires equality, so
neither the reader nor the model can drift alone.

**What is the format's:** exactly one backward crossing. The
end-of-central-directory record is at the end, so any directory-driven
reader must touch the last part first and can then go forward — and it
can, because the directory lists entries in increasing (part, offset)
order in all four cases (checked, not assumed). Reading local headers
forward from part 1 instead would cross zero times and is not worth it:
with flag bit 3 the sizes live in a data descriptor AFTER the data, so
the reader would be scanning for signatures rather than being told.

**What was ours** — everything else, and it came from two decisions,
both since reversed:

*A prepass over every part.* The parts were presented as one
concatenated stream so that `unc_zip_extract` could be reused verbatim,
and a concatenated stream has to know its own length before the record
at the end can be found. Learning that length means opening every part.

*A directory walk interleaved with the data reads.* One record, then
its entry's data, then back for the next record — about two opens per
ENTRY, which is why the overshoot tracked entry count rather than part
count.

**The correction worth carrying: a joined stream is not the only way to
read a format that addresses itself by part.** A spanned zip stores
(part, offset) pairs, so a reader that keeps them as pairs needs no size
table at all — position, read, and roll into the next part at EOF. The
sizes were an artifact of flattening the set into one address space, and
this entry originally called them "the address map... not an
inefficiency to remove", which was exactly backwards: they are the
address map only of the representation we chose. Both are gone
(`UncSegMap` is now `seek_part` / `skip` / `part_size`, and the joiner
has an ADDRESSED mode beside the flat one StuffIt still uses), and the
reader hits the floor on all four cases.

Three things fell out of it that were not the point but are worth
having. The 66,000-byte tail buffer every zip used to allocate to find
its directory record is gone, replaced by the 515-byte windowed scan
`fmt_zipseg.c` already had for the describe path — one scanner now,
where there were two doing the same job, and zip's peak heap dropped
accordingly (FORMATS.md ¶). The directory is read once into memory,
which helps a single-file zip too. And because that allocation can fail,
the old record-at-a-time walk is kept as the fallback: the bound on it
is the caller's budget rather than a constant chosen in the decoder,
which is the same rule the Arsenic block and the LZW table settled on.

**The one cost that had to be checked on the Mac rather than reasoned
about.** Recognizing the last part of a set means scanning backwards for
a record that can be 65,557 bytes from the end, and that probe sits
before most of the others — so on a Mac every archive the first seven
probes do not claim now pays a backwards scan off a floppy before its
format is even known. The argument that it is harmless is that the scan
is bounded by `min(size, 65 KB)` while extraction scales with the whole
file, so the ratio can only shrink as files grow; the worst shape is
therefore a LARGE file of the format probed last, which is BinHex.
Measured at authentic 1x on `macburger-helper.hqx` (306 KB): **132 s**,
against the 150 s recorded for it before this work (FORMATS.md, "7 MHz
Mac Plus"). Not visible, and the argument survives its own worst case.

**A caller-allocated struct that grows is a trap.** `UncVolumeSource`
gained an optional `size` callback here, and every existing caller —
the CLI, the Mac shell, and two unit tests — was filling the struct
field by field without zeroing it first, so the new member held whatever
was on the stack and the engine called it. The CLI segfaulted; **the
unit tests passed**, which is the part to remember. Callers now zero it
and the header says to.

**The generator being somebody else's code buys a fourth opinion.**
`tools/synth_sitsplit.py` writes StuffIt parts by hand because nothing
here produces them, which leaves that scheme adjudicated by `unar` and by
the generator's own intent. Info-ZIP is in this environment, so every
spanned case is built twice from the same input — split and unsplit — and
the unsplit archive is read by our own engine down a path that touches no
joiner and no address translation. A subtly wrong join now disagrees with
*us*, not only with the oracle.

## 2026-08-10 — `.NNN` splits: the payload is the adjudicator

The third segmentation scheme, and the one this repository had ranked
last and written off. `NAME.001` / `NAME.002` (source:
`reference/XADMaster/XADSplitFileParser.m`) carries no header, no
marker and no part count: the scheme *is* the naming convention. So
the descriptor is built by the HOST — `unc_segment_describe` never
returns `UNC_FORMAT_SPLIT`, because there is nothing in a part to read
it out of — and the engine joins a flat set whose length is the sum of
its parts.

**The claim that was wrong.** OPEN_ITEMS.md said a `.NNN` split "has no
structure to adjudicate the result against afterwards". True of the
scheme, false of the result: the joined stream is normally a `.sit`,
`.cpt` or `.zip` that states its own lengths and checksums, and the CLI
already hands a joined file to that reader through the envelope unwrap
chain. **A scheme that proves nothing can still inherit a proof from
what it joins into.** What it genuinely lacks, and spanned zip has, is
a declared part COUNT — so a set missing its TAIL is invisible to
everything except the payload.

**How far that inheritance goes was measured, not assumed**, because it
degrades in a specific place: swap two parts of a split zip and the
reader throws the set out on its own offsets and CRCs — *unless the
swap involves part 1*, after which the join no longer looks like an
archive at all, is emitted as the plain file this scheme is entitled to
produce, and nothing objects. Both halves are asserted in
`tools/run_segments.py` (`split_behaviours`), so the limit is
re-measured on every run instead of remembered. The API promise is
therefore weaker than spanned zip's by one step: *a wrong part cannot
pass silently while what it joins into can still be recognized.*

**Name beats content, deliberately.** XADSplitFileParser sits under
"over-eager detectors", second from last in `XADArchiveParser.m`, so
every content parser is tried first — and part 1 of a split `.sit`
begins with `SIT!`. Measured: `unar derived-Fractional_Widths.sit.001`
exits 1 having written one truncated fork, and `lsar` calls it StuffIt.
That is the shape these sets actually have in the wild, so the CLI
decides by name BEFORE the sniff (`--no-parts` puts the sniff back in
charge). **A limitation of a parser's priority order is not a
limitation of the scheme.**

**Two departures from the reference, both because it joins whatever the
directory scan returns:** the run must be consecutive from `.001`, and
a member numbered past the end of the run is treated as evidence that
the gap is a missing part rather than as another part. A stray
`NAME.900` beside a valid 3-part set is appended by the reference
silently — 10,200 → 10,208 bytes, measured, and re-measured by the
suite so the departure cannot quietly stop being one. Recognition is
widened the same way: the reference requires one SPECIFIC sibling, so a
set whose `.002` is the missing one is reported as an unknown format
with its `.003` sitting beside it; any member will do here, and the
missing part is then named.

**The gap is resolved before extraction, not disk by disk.** For the
other two schemes the volume source is asked lazily. Here the joined
LENGTH is the sum of the parts' lengths — nothing states it anywhere —
and it is the size the one emitted entry announces, so every part has
to be located up front. `--ask` therefore prompts before the first byte
is written. A host that cannot answer `size` for nothing gets
`UNC_ERR_CORRUPT` rather than a guess.

**What it cost to build: 25 lines of engine.** The flat mode already
was this join with `head_len = 0`, and `unc_sitseg_emit` already was
"one entry, name and sizes from a descriptor, forks streamed from the
joined stream". The rest is host-side name discovery in `cli/main.c`.
The ranking rule from 2026-08-08 — *a part must be identifiable from
its own bytes* — put this scheme last and that was right about the
strength; it was not a reason not to build it.

**A test that passed for the wrong reason, caught by mutating the
code it was supposed to test.** The stray-member case used `NAME.900`,
which trips the 256-part ceiling check — a different branch — so
removing the consecutive-run rule entirely left it passing. It is
numbered `n+2` now, and the ceiling has its own case beside it.

## 2026-08-13 — parts inside envelopes, and rationing the search

A real download of a segmented set is not a set of parts. It is
`Archive.sit.1.hqx`, `Archive.sit.2.hqx`, …: every part BinHex- or
MacBinary-encoded on its own, because that is what carried a Macintosh
file over a 7-bit network. Until now this program took the envelope off
*after* the join — the wrong order — and the shape failed: measured
2026-08-13, part 1 unwrapped into the output directory, discovery found
no siblings there, and the run ended in `UNC_ERR_SEGMENTED` having
written a truncated `Test.sit` and left the intermediate behind.

**The join is the layer that has to move, not the envelope.** So
discovery gained one thing: a candidate that is not a part in its own
right is tried as an envelope holding one. It is entirely host-side —
`cli/main.c`, no engine change — because opening files is the host's
job and the engine already accepts parts through a callback.

**Only the StuffIt scheme is looked for this way**, and the reason is
the one that ranked the three schemes in the first place: a StuffIt
part carries its header IN the payload, so unwrapping is all that
stands between the file and the same fingerprint check every other part
gets. A spanned zip part or a `.NNN` split part is placed by its
FILENAME, and the filename of a wrapped part is the wrapper's — no
reference implementation says what that should look like, and inventing
a convention is what rule #1 forbids.

**What the search is rationed by, and the first answer was wrong.**
The first version looked inside envelopes when the part it was handed
had itself come out of one — the shape of part 1 as evidence about the
set. It works, and the assertion written to defend it could not fail:
with the ration removed, a complete set beside a spare envelope still
passed, because a part already located is skipped *before* anything is
printed. The observable was a consequence of the search, not the search.

Two things came out of fixing that, and the second is the better
design. The cost is now reported by the decode itself (`looked inside
X` under `-v`), so what is asserted is the work rather than its effect.
And the ration became **need, not shape**: the raw scans run first, and
envelopes are opened only if the set is still short of a part —
`seg_have_all` sums the located parts' payloads against the fork
lengths the StuffIt header states, which is the same sum that ends the
joiner's walk. A complete set opens nothing beside it however many
envelopes are lying there; a short one pays a hundred decoded bytes per
envelope rather than failing. The peek stops at `UNC_SEG_HEAD` bytes
and a part is decoded whole only once it has proved it belongs.

This is strictly more capable than the rule it replaced, and by
accident rather than design: a **half-unstuffed** download — some parts
already unwrapped on disk, one still in its envelope — now joins, and
it was never a shape anyone set out to support. **A ration tied to what
is missing subsumes one tied to what the first part looked like.**

**What it buys, measured against the reference.** `unar` handed part 1
of a wrapped set unwraps that one part, writes it out and **exits 0** —
success, with a fragment, which is the same silent-truncation class as
the bare-relative-path trap already documented in `run_segments.py`. It
is asserted rather than remembered: if the oracle ever joins one, the
suite says so. Parts wrapped in different envelopes, under names that
say nothing (`zzz-download.bin`) or actively lie (`Other.sit.9.hqx`),
scattered across three directories, join byte-exact — because after the
envelope comes off, identity is where it always was.

The suite's four new assertions were each shown to fail before being
believed (`tools/run_segments.py`, `wrapped-*`): with the search
disabled, with the ration removed, with the cleanup removed, and with
the foreign decoy replaced by the genuine part.

## 2026-08-14 — Compact Pro segments: the layout, derived from specimens

Every other format in this engine was transcribed from a reference
implementation. This one could not be: `unar` reads the archive volume
byte and discards it, `macunpack` stores its copy unused, and The
Unarchiver's own format wiki marks all three of the fields involved —
volume, cross-volume magic, per-entry volume — "meaning not entirely
clear" (`reference/notes/cpt_specs_theunarchiver.md`). There is no
sample in the corpus and none in the public archives: segmentation moved
archives between people on floppies, it did not distribute them.

**So the specimen was made by the only implementation that writes the
format.** `tools/vmac/cptsegment.py` runs Compact Pro 1.51 — unpacked
out of the corpus by our own CLI — on System 6.0.8 under Mini vMac,
opens an archive the differential suite already adjudicates, and drives
`Misc > Segment` with a chosen segment size. What comes back off the
volume is a real segmented set, written by the application, and the
archive it was cut from is ground truth that owes nothing to any of
this.

**Two specimens, chosen for different shapes**, because one set cannot
tell "always" from "coincidence": `edu3` is 4 segments of a 9-file
archive with folders, `biplane5` is 5 segments of an archive holding ONE
entry, whose data therefore straddles all four boundaries.

What both say, measured rather than read:

- Each segment begins with the SAME 8-byte header as an ordinary
  archive: `01`, a volume number, a 16-bit set identity, and an index
  offset.
- Volume numbers are 1-based and consecutive: 1..N.
- **The identity is one value shared by every segment of a set**, freshly
  generated and not the source archive's (0xD2CF and 0xDE46 here, from
  sources 0x9438 and 0x81DF). That is the "information inside the files
  to determine their proper ordering" the author's manual describes, and
  it is why the manual can promise that names and locations do not
  matter. It matches the corpus: the same field is distinct in all 68
  single-volume archives.
- **The index offset is 0 in every segment but the LAST**, which carries
  it relative to its own start. That is the byte-level form of the
  manual's "you must open the FINAL segment".
- **The payload — each segment minus its 8 header bytes, concatenated —
  is byte-identical to the source archive's data region**: 84,467 bytes
  and 106,790 bytes, exactly. Segmenting re-chunks the archive and
  rewrites the directory; it does not recompress anything.
- An entry is addressed as **(volume, offset within that volume's
  file)**, offset counted from the segment's own start, header included.
  Every entry's pair maps to precisely the flat offset the unsegmented
  archive used — checked for all 9 entries of one and the 1 of the other.
- Entry data crosses segment boundaries freely, skipping the 8-byte
  header of each segment it continues into.

So the scheme is **zip-like in its addressing and StuffIt-like in its
identity**: parts are located by content, and the reader must translate
(volume, offset) rather than flatten. The ranking rule from 2026-08-08 —
*a part must be identifiable from its own bytes* — puts it at the top of
the unbuilt schemes rather than the bottom, which is the opposite of
where OPEN_ITEMS.md had it.

**What a derived layout has to carry that a transcribed one does not.**
Every field above is a statement about two specimens, so the parser
records what would falsify it rather than citing a source that says it
is so: a set whose identity differs between segments, a non-final
segment with a non-zero index offset, or an entry whose (volume, offset)
does not land in the volume it names. The suite asserts all three
(TESTING.md), and the real specimens are what the Python generator is
validated against.

**And one thing not to repeat.** The second case was first pointed at
`alpha401.cpt`, which is a MacBinary file holding a `.cpt` — that is how
it was uploaded — so the Mac got a PACT-typed file whose data fork is an
envelope and Compact Pro said it was "damaged or has a format which this
version does not recognize". Six minutes of emulator to learn what the
first two bytes say. The harness now refuses a source that does not
begin `01 01`, and the corpus's `derived-*.cpt` copies are the unwrapped
ones. **A fixture's extension is a claim about it, not a fact.**

## 2026-08-14 — reading a Compact Pro set: addressed mode, and the index

The layout was derived the day before; this is what reading it took.

**It is the ADDRESSED mode, not the flat one.** A Compact Pro entry
carries the volume its data lives in and the offset within that
volume's file, so the pairs are already there and flattening them would
mean measuring every segment before extraction began — the prepass that
mode exists to avoid (DECISIONS.md 2026-08-09). The reader positions at
(volume, offset) and rolls forward, exactly as the zip reader does, and
`unc_cpt_extract` gained the same two helpers `zip_seek`/`zip_skip` are.

**Rolling into the next part starts at `head_len`, not at 0.** A spanned
zip's parts concatenate with nothing to strip; every Compact Pro segment
repeats the 8-byte archive header. The first version rolled to 0 and
**9 of 11 entries came out byte-exact** — the two that failed were
exactly the two whose data crosses a cut. A bug that only shows on
straddling entries is invisible in any archive small enough to fit in
one segment, which is most of them.

**The index is read once, and that is worth an allocation.** Every
entry's record lives in the final segment and its forks live wherever
the entry is, so walking record-by-record alternates between two
segments — 19 part opens with 8 backward crossings on a 4-segment set
whose floor is 5 and 1. On a floppy each of those is a disk swap. The
index is now buffered for the walk, and the suite requires the measured
opens to equal a floor derived in Python from the archive's own
directory.

**It is allocated LAST, after the working buffers, and that is not an
implementation detail.** Allocated first it would compete for memory the
decode genuinely needs, and on a small machine a large index would
starve a small archive. Last, it takes what is left: refused, the walk
reads each record where it lies and produces the same bytes for more
crossings. Measured at one byte under the run's own high-water mark:
5/1 becomes 19/8, tree identical, and `ci.sh` asserts both halves.
**An optimisation that can starve the thing it optimises is not one.**

**What `unar` does with a set, measured 2026-08-14.** Given the final
segment it calls the file a whole Compact Pro archive — `lsar` agrees —
reads every entry at an offset belonging to another volume, fails most
of them with "Attempted to read more data than was available", writes
the rest as garbage, and **exits 0**. Given the first segment it says
"Couldn't recognize the archive format" and also exits 0. That is why
the segment probe runs before the plain one in `unc_sniff`: the final
segment of a set is exactly the file a user opens, and it is the one
that most looks like an ordinary archive. Asserted in the suite, so if
the reference ever learns the scheme this repository finds out.

**Any segment opens the set, which the application itself cannot do.**
The manual is explicit that "you must open the FINAL segment"; every
segment carries the set identity, so a reader that discovers by content
has no reason to require one in particular. Opening parts 1, 2 and 3 of
a 4-segment set gives the same tree as opening part 4.

## 2026-08-14 — the Macintosh shell learns the other three schemes

The engine had four segmentation schemes and the application had one.
Closing that took two pieces, and the second is the interesting one.

**Compact Pro needed a search, not a matcher.** Its parts are matched by
header, which `SegPartOf` already did through `unc_segment_match` — so a
set opened at its FINAL segment would have joined without any change at
all. What was missing is every other case: the part count lives only in
the last segment, so a set opened anywhere else has no count and the
joiner cannot start. `SegFindLast` asks each part found so far, 8 bytes
at a time, until one answers with one. Then the whole scan is thrown
away and redone, because with a count in hand the match rule is
stricter — a middle segment must not carry an index and the last one
must — and two bytes of identity is not much to let a file in on.

**Spanned zip and `.NNN` splits needed a name matcher**, which this
application had deliberately never had: "a part is identified by its
header, never by its filename" is the property that makes a StuffIt set
work when its parts are scattered and named unlike each other. Neither
of these schemes can be matched that way — only the first and last part
of a spanned zip identify themselves at all, and a split part never
does — so the shell now decides by NAME first, exactly as the Linux CLI
does and for the same reason: part 1 of a split `.sit` begins with
`SIT!` and would otherwise be read as the truncated archive it is a
slice of. What keeps a wrong file out is not the scan but the check the
engine makes on the ASSEMBLED set.

The names arrive as Str63 — a length byte and MacRoman bytes — so the
comparisons are written out rather than borrowed from a libc this
application does not link. That is where the one real bug was: the
`.zNN` test measured the extension one byte short, so the `.zip` member
was found and the numbered parts were not, and the set failed as damaged
rather than as incomplete. **The `.NNN` scheme's arithmetic was right,
so a passing split case said nothing about the zip one** — two schemes
sharing a function do not share its bugs.

**A split needs every part's LENGTH before extraction starts**, since
the sum is the joined size and nothing states it anywhere. On a Mac that
is `PBGetCatInfoSync` per part — a directory lookup, not a disk swap —
and it is what OPEN_ITEMS.md said would have to be decided. It costs
nothing the user can see, so it is simply done up front.

**And the harness bug, which is the fourth of its kind in this
directory.** The new phase opens the first row of Standard File. The
boot volume's root holds an invisible `Desktop` file, and `Set.z01`
sorts after it while `Blob.001` sorts before — so the split case passed
and the zip case opened `Desktop`, which is not an archive, and the
application said so. A photograph of correct behaviour that reads
exactly like a defect. The sets are now named to sort first, which is
deterministic rather than lucky. **What made this cheap to find was
putting the engine's return code in the alert**: `ret=-1 fam=0` said
in one frame that the application had never seen a family at all, where
the screenshot alone had already sent me to re-read the matcher twice.

## 2026-08-14 — the Macintosh application takes ALL the envelopes off

Asked for `Archive.sit.1.hqx` on the Mac, and found something else
first: the application had no envelope unwrap at all. Opened on
`boogers-152.hqx` it wrote `boogers152.sit` and stopped — measured, not
inferred — where the Linux CLI has always gone on to the contents.
README.md has promised the second behaviour since it was written, which
makes it the first user-facing claim in this repository that the
software did not honour (BLOCKERS.md, *Withdrawn claims*).

It also blocked what was asked for. A wrapped set is
`Archive.sit.1.hqx`: the envelope has to come off part 1 before anything
can notice that what is inside is a segment. No unwrap, no wrapped
parts.

**The loop is in the interactive path only.** The autotest keeps
single-layer semantics because every manifest it is graded against
describes one layer (`tools/vmac_check.py`), and 55/55 depends on that.
So `RunExtract` reports the SHAPE of what it wrote — one file and no
folders is what an envelope yields — and `ExtractOne` sniffs that file
rather than trusting its name, goes round, and deletes the layer it came
from once the next one has succeeded.

**And the bug that cost a run: a delete after the last flush is not a
delete.** `RunExtract` calls `FlushVol` before returning, so removing
the intermediate afterwards left the change in the volume's cache — the
harness kills the emulator where a person would quit, and the file was
still there on the image. The extraction was right and the tidying up
was invisible. Anything this application does to a volume AFTER an
extraction has to flush for itself.

**Wrapped parts then followed the CLI's shape**, with one difference
that is the whole reason it was ranked last: a decoded part needs
somewhere to live. On Linux that is a temp file beside the output; here
it is `unclassic part N` on the OUTPUT volume, deleted when the join is
over — the one place this application knows it may write. The search is
rationed the same way, by `SegHaveAll`: envelopes are opened only while
the set is short of a part, so a complete set opens nothing. StuffIt
only, for the reason the CLI gives.

Verified through the real UI at 4 MB and at the 1 MB floor target: part
1 as `Apart.sit.1.hqx`, part 2 as `zzz-download.bin` (a different
envelope, a name that says nothing), part 3 as `Other.9.hqx` — joined,
extracted, and nothing of ours left on the volume, against the Linux
CLI on the same three files.

## 2026-08-14 — the detect-only claim had no test, and LZH stays out of scope

Asked why LZH is out of scope, and the answer in the documents was thin —
"the optional half of M8" — while the evidence for it is strong and was
never written down: **the corpus contains no `.lzh` at all**, measured
over every fixture. Macintosh software was essentially not distributed
that way; LHA belonged to the Japanese PC world and the Amiga. Compact
Pro's LZH is a different algorithm from LHA's, so nothing here is a head
start either: macutils keeps them in separate files (`cpt.c` +
`huffman.h` against `de_lzh.c`), and so does XADMaster. Extraction would
be ~550 new lines for a format the target platform did not use.

**What the question did turn up is that the detect-only claim was
untested.** Five formats are named but not extracted, and the promise —
`unc_sniff` names them so a UI can say what the file is — had nothing
behind it for LZH or StuffIt X. Worse, `run_diff.py` SKIPPED any fixture
whose format it does not extract, counting it as a "format pending", so
the 6 DiskDoubler and 1 Now Compress fixtures in the corpus were
asserted on in no way at all.

They are graded now, on exactly what the claim promises: the name agrees
with the oracle's, and extraction refuses without writing anything.
8 fixtures, and "formats pending" is 0.

**One real LZH file was added to the corpus on purpose**, and it is the
only fixture here that is not Macintosh software: an Amiga `-lh5-`
archive from Aminet. That is the point — the corpus has none because the
platform had none, so testing the probe needs one from outside, and
`fixtures/SOURCES.md` says so where somebody will find it.

**And a limit worth stating rather than discovering later.** The refusal
is guarded twice — `unc_format_extractable` in the CLI and the `default:`
arm of the engine's dispatch — so mutating either alone changes nothing
the test can see. It catches "this format silently became extractable and
succeeded", not "one of the two gates broke". Both mutations together do
fail it, which is how that was established rather than assumed.

## 2026-08-14 — one command to replay the segment work, and what it caught

Every segmented-archive scenario had been verified on the Mac by a
command typed once. `tools/vmac/segcheck.py` is those commands in one
place — seven scenarios across both harnesses, each saying what it would
mean if it failed. `sample.txt` cannot carry them: it is a flat list of
fixture names and the autotest opens a file called `archive.sit`, while
a set needs extra files beside it or its own real filenames.

**It failed on its first full run, twice, and both were right to fail.**

*The StuffIt case was checking the wrong thing.* That scheme yields the
JOINED ARCHIVE — one file — where the fixture's manifest describes what
is inside that archive, so the on-screen grid can never match it. The
disk is the only honest check there, and the scenario now reads the
joined file back off the Out volume and compares it to the archive it
was cut from. Compact Pro is the opposite: its reader emits the
archive's entries directly, which is exactly what the manifest lists, so
the grid is right for it. **Two schemes that look alike from the outside
want opposite oracles.**

*The zip and split cases had been overtaken by that morning's own work.*
Their payloads are archives, and the envelope unwrap added hours earlier
now extracts what the join produces and deletes it — so a phase looking
for the joined file found nothing. The application was right and the
expectation was a day old.

**And fixing that turned up a genuine defect: the two hosts disagreed.**
The Linux CLI unwraps only ENVELOPE formats — MacBinary, BinHex,
AppleSingle/Double, gzip, `.Z` — plus the segment schemes that yield the
file they were cut from. My Mac loop unwrapped anything that produced
exactly one file and no folders, whatever produced it. So a zip holding
a single `.sit` was extracted twice on the Mac and once on Linux:

    volume:  Demo Manual V1.6, EB Sounds, Empire Builder V1.6.1 Demo
    CLI:     payload.bin

The CLI's rule is the considered one — an archive that happens to hold
one archive is still an archive, and its contents are the answer. The
shell applies the same predicate now, and learns the format for free:
`unc_extract` sniffs internally, so sniffing explicitly and dispatching
with `unc_extract_as` costs nothing and tells the caller what the layer
was.

**Nothing would have found this except running both hosts against each
other.** The Mac phases compared against the Linux CLI, which is why a
divergence introduced on one side showed up at all — and it showed up
the same day rather than in a user's hands, because the scenarios were
written down as a script instead of left in a terminal.

## 2026-08-15 — measuring this project against StuffIt Expander 4.0.2

Everything this repository knows about "enough" has been self-referential:
the corpus, the oracle and the milestones are all ours. The one external
yardstick available is what a user of a real Mac Plus would otherwise
have run, and it had never been applied.

**A competitor's documentation is a primary source, and it ships inside a
file we can already read.** Expander 4.0.2's distribution is MacBinary
around a StuffIt self-extracting archive around a 400K HFS image; our own
CLI walked the chain and produced an image byte-identical to `unar`'s, and
its Read Me, its "What's new" file and its alert strings answered every
question the comparison needed. No web page was needed for a single claim
about 4.0.2's behaviour — the web was used only for dates. The tables and
their sourcing are in FORMATS.md, "Compared with StuffIt Expander 4.0.2".

Three things came out of it that were not visible from inside:

- **A rival's stated limitation is a claim about the problem, not only
  about the rival.** *"StuffIt Expander cannot expand encrypted or
  segmented Zip or Compact Pro files"* is its Read Me admitting the two
  hardest segment schemes — and those are exactly the two M11 built after
  ranking them as the ones a part cannot prove itself in. The ranking rule
  and the era's own tooling agree about which end of the problem is hard,
  which is the first outside confirmation the M11 ordering ever had.
- **The free tool's floor is a system version, ours is a machine.** Expander
  runs from System 6.0.5, but everything beyond `.sit`/`.cpt`/`.hqx`/`.bin`
  lives in an add-on its Read Me calls *"a System 7-only shareware
  product"*. So on the exact machine this project floors at, the standard
  tool is four formats and one segment scheme, permanently. That is the
  gap this project actually fills, and nothing in the repository had said
  so.
- **An oracle you share a blind spot with cannot show you the blind
  spot.** Expander claims multipart BinHex — several documents in one text
  file, the shape comp.binaries.mac produced. We take the first document
  and exit 0; `unar` does the same, so 179 BinHex fixtures and a
  differential suite could never have caught it. It is filed in
  OPEN_ITEMS.md section 5 with the reproduction. The lesson generalises
  past BinHex: **the differential suite can only find defects the oracle
  does not share**, and the cheapest way to find the shared ones is to ask
  what some THIRD implementation claims. That is the same move that closed
  StuffIt method 6 with macunpack, arrived at from the other direction.

What this comparison is not: Expander was never RUN here. Every row in its
column is documentation, labelled as such in FORMATS.md, and the one number
it would have been nice to have — the memory partition the application asks
for — is unmeasured, because reading a `SIZE` resource off that HFS image
needs a reader this machine does not have.

## 2026-08-15 — several BinHex documents in one file, and the oracle's blind spot

**Claim:** a `.hqx` can hold more than one document; this decoder read the
first and returned success. **Evidence:** `cat a.hqx b.hqx` listed and
extracted one file, exit 0. **Consequence:** every posting that carried two
attachments silently lost all but the first.

The fix is small — after a document's terminating ':' , look for the next
banner and decode again — and it is transcribed rather than invented:
`reference/macutils/hexbin/hexbin.c` decodes a document and then does
`again = 1; goto nexttry`, its `find_header()` scanning on to EOF. Three
things about it are worth keeping:

- **The banner scan had a limit that was right once and wrong afterwards.**
  32 KB is a sane bound for finding the FIRST banner, since a file that is
  not BinHex should be given up on rather than read whole. Applied to the
  second document it would have made the fix work in extract mode and fail
  in list mode, where the previous document's stream is never consumed and
  the distance to the next banner is the size of the file. A bound derived
  from one caller's situation does not survive a second caller.
- **A banner with nothing usable after it is an error, not a quiet stop.**
  The tempting alternative — treat any failure after the first document as
  "end of file" — reintroduces exactly the defect being fixed, in a place
  nobody would look for it again.
- **`unar` shares the limitation, so the differential suite was blind by
  construction.** 179 BinHex fixtures and 3,740 corrupt variants could not
  have caught this at any point, and the size of that suite is precisely
  what made the gap feel impossible. The way out was a THIRD oracle:
  macutils' `hexbin` has handled the case since 1991, and it now grades the
  concatenated fixtures in `ci.sh` (TESTING.md). This is the macunpack
  lesson from the other direction — that one was *a limitation that names
  one tool is a limitation of that tool*; this one is **a limitation you
  share with your oracle is invisible until a different implementation is
  asked.**

Both new suites were shown to fail before being believed: a one-line mutation
(decode one document and stop) fails 6 unit checks and all four assertions of
`tools/run_multihqx.py`, including the `hexbin` one.

The other half of what StuffIt Expander 4.0.2 calls multipart BinHex — one
document broken across several postings — is NOT this. What this engine joins
is a document cut across files named `.001`, `.002`, which the plain-split
scheme already did (FORMATS.md, comparison table).

## 2026-08-15 — DiskDoubler in scope: three containers, four methods, and two traps

DiskDoubler and Now Compress were both out of scope by the brief and named
detect-only in five status files. The maintainer put them in scope; this is
what DiskDoubler took, and why Now Compress did not land with it.

**What is implemented is what the corpus can grade.** Three containers (a
single compressed file, `DDAR`, `DDA2`) and methods 0, 6/9, 8 and 10 — every
method the six fixtures use. Methods 1, 2, 3, 4, 5 and 7 are declined per
entry, because the reference marks two of them unimplemented and one untested,
and none appears in any fixture: code no oracle can grade is not a feature,
it is a liability with a version number. Same rule that keeps LZH extraction
out.

**Method 8 is Compact Pro compression in a DiskDoubler container**, so it is
`fmt_cpt.c`'s two stages with one parameter changed: the Huffman block is
0xfff0 here against 0x1fff0 there. That made three functions and two structs
move into `unc_internal.h` rather than be copied — the alternative was a
second copy of an LZH decoder that 108 fixtures already exercise.

Two traps, both worth carrying:

- **`unc_bufin_tell()` counts from the last `unc_bufin_init()`, not from the
  start of the file.** DDn addresses three sub-streams by absolute offset and
  seeks between them, and every seek re-bases the buffer — so the first
  version computed `literalstart`, `lengthstart` and `nextblock` against a
  moving zero and produced offsets like 42. The decoder now carries an
  `origin` and adds it. **A position helper is only absolute if nothing
  re-bases the thing it measures.**
- **A short read is invisible until the optimiser exposes it.** The `DDAR`
  entry header is 124 bytes and the walk read 120 of them, so `rsrccrc` came
  from uninitialized stack. At `-O0` that stack held zeros and the check was
  skipped; at `-O2` it held `"ttxt"` and the entry failed its checksum. The
  fixtures could not see it either, because every DiskDoubler file in the
  corpus takes the other branch — **the unit test written for coverage found
  it within a minute of existing**, which is the argument for fixture-free
  tests in one line.

**Now Compress is not the same job.** Its archive is SOLID — every fork of
every file in one compressed stream, entries addressed as (offset, length) —
which is a container model this engine has never had, and the codec is a
517-line handle against a single fixture. It stays detect-only, and the
detect-only claim stays tested (`run_diff.py` keeps it in DETECT_ONLY).
OPEN_ITEMS.md has what would close it.

**Neither format has multi-segment anything.** The request was conditional on
that, so it was checked rather than assumed: `XADDiskDoublerParser.m`,
`XADNowCompressParser.m` and macutils' `dd.c` contain no concept of a part, a
volume or a continuation, and no header field in either format numbers one.
DiskDoubler split *disks*, not archives — the multi-segment work of M11 has no
counterpart here.

## 2026-08-15 — Now Compress without the solid stream

The reference reads a Now Compress archive as one SOLID stream: every fork of
every file concatenated, entries cut out of it by (offset, length). That is
why this was written up as a container model the engine had never had, and
why it was ranked as a second job rather than more of the first.

**It does not have to be read that way.** The parser hands the decompressor a
list of per-file start offsets, and each file's stream holds exactly that
file's resource fork followed by its data fork — the solid offsets are just
the running sum of those. So this reader opens one stream per file and serves
two forks out of it, which is the shape the engine already has, and which is
what keeps the whole format to a **flat 128 KB**: history, block, staging, all
fixed by the format rather than by the archive. A solid reader would have had
to hold or re-decode the stream to reach a late entry.

**A rediscovered structure beats an inherited abstraction.** The reference's
solid-stream machinery exists because XADMaster has it and it is free there;
transcribing it here would have imported an architecture to solve a problem
this format does not actually have.

**One fixture is not coverage, and the mutation says so.** The corpus has a
single Now Compress archive; instrumenting the block loop shows it reaches two
of the five block shapes, with one file, one fork and no folders. The unit
test `test_nowcompress` builds the container synthetically — a folder, a file
with both forks, stored blocks — and its worth is measurable: **serve the two
forks in the wrong order and the unit test fails while the fixture still
passes 1/1**, because the fixture has no data fork to get wrong. What neither
reaches is written down in OPEN_ITEMS.md, including a checksum-driven search
for a wrong offset delta that has never once fired here.

## 2026-08-15 — the emulator harness graded fixtures against other fixtures

**Claim:** two Mini vMac tiers run in parallel, as this repository's own
harness README recommends, can grade a fixture against another fixture's
screen. **Evidence:** the 4 MB and 1 MB tiers started together; three fixtures
failed at 4 MB and two at 1 MB, and the failing rows reported file counts,
peak heaps and fork lengths that belonged to archives from the OTHER run —
`derived-MacPass390.sea` "failing" with `derived-DD_Expand.sea`'s 102,432 B
peak and 270,362 B resource fork. Re-run serially, all of them pass.
**Consequence:** every parallel run this project has ever done was liable to
it, and the same five fixtures pass 61/61 on both tiers once the cause is
fixed.

The cause is check-then-act. `Display.__init__` scanned for an `n` whose
`/tmp/.X<n>-lock` did not exist and then started Xvfb on `:n`. Two processes
both saw `:90` free; the second Xvfb exited immediately because the lock was
taken, and nothing checked that it had — the readiness probe,
`xdotool getdisplaygeometry`, succeeded against the FIRST run's server. From
there both runs pointed the emulator and `import` at one display.

Two things worth carrying:

- **A readiness probe that does not identify what it is talking to will
  happily confirm somebody else's server.** The probe was doing its job; it
  was asked the wrong question. Xvfb now picks the display itself with
  `-displayfd` and tells us which, so the answer cannot be another process's.
- **The failure mode was a wrong verdict, not an error.** Nothing crashed,
  nothing warned; a format that works perfectly was reported as broken, and
  the numbers in the failure message were the tell. Had two fixtures happened
  to share an aggregate, it would have been a false PASS instead. A harness
  whose two instances can silently share a channel does not have a flakiness
  problem, it has a correctness one.

## M13 — ARC and uuencode: a generator that agrees with you proves nothing

**2026-08-15.** The brief became "everything StuffIt Expander 4.0.2 expands",
which named four formats. Two are delivered (`.arc`, `.uu`); two are not
(AppleLink `.pkg`, StuffIt SpaceSaver), and the reason is worth separating
from the work.

**Neither delivered format occurs in the corpus.** Both are therefore graded
the way M11's segmented sets were: generate the archives, then hand them to an
implementation that is not ours. For ARC that is `unar`; for the UUTool shape
of `.uu` it is macutils' `hexbin`, the implementation the decoder was
transcribed from. Debian's `arc` 5.21q, fetched by `tools/get_arc.sh`, adds
archives whose bytes owe nothing to this repository at all — but it only emits
methods 2, 4, 8 and 9, and macutils says ArcMac used 1 to 7, so the generator
is not optional.

**Twice, our decoder and our generator agreed with each other and were both
wrong.** The crunch decoder (methods 5/6/7) read its 12-bit codes LSB-first;
`tools/synth_arc.py` mirrored the same reading, so every generated archive
round-tripped perfectly — and the CRC-16 agreed too, because ARC's checksum
covers the DECODED bytes, which were correct. `unar` refused all three
methods. The fix is one call: XADARCCrunchHandle reads `CSInputNextBitString`,
and in XADMaster it is the **LE-suffixed** variant that means LSB-first
(`reference/XADMaster/CSInputBuffer.h`), so these codes are MSB-first. The
second was the same shape: the compress encoder for methods 8/9 added a table
entry on every code, where the decoder adds one on every code *except the
first*, so it widened its codes one step early — again invisible in a round
trip, again caught by `unar` and by our own decoder agreeing with each other
against the generator.

**The lesson is the one this repository keeps relearning from the other
direction.** "Ask what evidence a tolerance rests on; if the answer is our own
output, it cannot fail" (2026-08-08) was about a skip. This is the same
sentence about a fixture: **a generator written from the same reading as the
decoder tests the reading, not the format.** A round trip is a self-portrait.
The oracle is the only part of the arrangement that can disagree, which is why
neither format was allowed into the suite without one.

**What is declined, and the difference between the two reasons.**

- ARC methods 0x0a (Crushed) and 0x0b (Distilled) are PKARC's. Nothing
  reachable writes them, so an implementation could not be graded — the
  DiskDoubler rule (2026-08-15), unchanged.
- **ArcMac** is different and worth recording. Its entries ARE walked: the
  Mac header is documented in `reference/macutils/macunpack/arc.h`, offset by
  offset, so name, type, creator and both fork lengths come out and the entry
  is reported. What is refused is the payload, because the entry's single
  stream holds both forks and no source anywhere says which comes first.
  macutils would have said — `macbinary.c` calls `arc()` — but **`arc.c` is
  absent from the macutils distribution, upstream tarball included** (checked
  2026-08-15). Now Compress is the reason this is not guessable by analogy:
  its streams hold the resource fork BEFORE the data fork, the opposite of
  the order the header lists them in (2026-08-15). A coin flip with a 50%
  chance of silently producing swapped forks is exactly what rule #1 exists
  to prevent.
- **AppleLink `.pkg` and StuffIt SpaceSaver are not delivered at all**, and
  the searching is recorded so nobody repeats it: the only AppleLink format
  with a published layout is the Apple II `.acu` ("fZink", CiderPress2's
  format notes), which that documentation explicitly distinguishes from the
  Macintosh Package format; SpaceSaver has no specification and no open
  implementation, and Aladdin's own later Expanders dropped it. Neither can
  even be SNIFFED without inventing a magic number. The route that would work
  is the one Compact Pro segments took (2026-08-14): drive the original
  application under Mini vMac and derive the layout from specimens it
  produces. That needs a specimen and a copy of the tool, and this environment
  has neither.

**One implementation detail worth carrying.** `unc_bufin_tell()` counts from
wherever the buffer was initialised, not from the start of the file. fmt_uu.c
re-initialises a buffer per document (it reads each document twice — the
Finder info that gives a Mac file its type sits at the END of the document,
and the sink needs it before the first byte), so every offset it keeps has to
be made absolute. Getting that wrong looked exactly like a corrupt second
document in a multi-document file, and only in the second one.

## Multipart postings: the other half of "split", and what each format can prove

**2026-08-15.** "Every type that does split files should be decoded" turned
out to name two different things, and only one of them was already built.

**What is a split archive, per the references.** XADMaster ships exactly two
split parsers — `XADSplitFileParser` (plain `.NNN`) and
`XADStuffItSplitParser` — plus spanning inside the zip parser; Compact Pro's
scheme has no reference at all and was derived here (2026-08-14). Everything
else was checked and has nothing: **ARC has no volume, part or segment concept
anywhere** — not in `XADARCParser.m`, not in macutils' `arc.h` or its ArcMac
notes, not in the `arc` 5.21q man page — which is the same answer DiskDoubler
and Now Compress gave. So M11's four schemes are the whole of it, and no new
joiner was needed.

**What was missing is the TEXT formats' version of splitting**, which is not
an archive scheme at all: one file posted as several mail messages. Joining
the parts — by hand, or by the `.NNN` scheme this engine already has — leaves
each posting's header sitting in the middle of the encoded stream.

- A **clean** cut joined and decoded already: `hello.uu.001` / `.002` works,
  because a split's ground truth is whatever archive it joins back into.
- A **realistic** one did not, for BinHex *and* uuencode: `From:` ends a
  BinHex document, since `:` is its terminator, and a mail header is not a
  uu line. Both came back as errors.

**hexbin was doing it all along**, which is the recurring shape: a limitation
that names one tool. `hqx.c` checks each LINE for "intermediate garbage" and
skips the whole line when it finds any — measured here, it decodes a
posting-shaped file byte-for-byte identically to the unsplit one. The rule
works because the BinHex alphabet omits `n`, `o`, `s`, `t`, `u` and the space:
ordinary prose disqualifies itself within a few characters. Our reader
filtered invalid CHARACTERS instead, which keeps the valid ones out of a junk
line and then stops at its colon.

**Only half of hexbin's rule is transcribed, and the half left out is the
interesting one.** It also skips any line whose length differs from the first
line's, with a look-ahead exception for the last. That test can discard a
legitimate short final line — hexbin ships `-c` to turn it off, which is the
reference admitting the same thing — and what it would have caught here is a
junk line built only of alphabet characters. **BinHex can afford to drop that
half because it carries per-fork CRCs**: a wrongly-accepted line becomes a
per-entry checksum error, not silence. That is asserted, not assumed
(`tools/run_multihqx.py` feeds it `AB:CD` mid-stream and requires a non-zero
exit).

**uuencode cannot afford the same reasoning, and the difference is the point.**
It has no length and no checksum anywhere, so the line test has to come from
the format itself — and it does: a uu line's first character declares how many
bytes it encodes, so a line whose length disagrees cannot be data. That
disqualifies every header shape measured. What no test can recover is a part
that never arrived: a set missing its MIDDLE part decodes to a short file and
nothing objects. A missing LAST part is still caught, because the terminator
and `end` live there. **The limitation is asserted rather than described** —
`tools/run_uu.py` builds a gapped set and requires the short, silent result —
so the day uuencode grows a check nobody knew about, the suite says so.

**Both new assertions were run against a mutant** with the line rules removed,
and both fail there. A test for a tolerance is worth nothing until the
intolerant build has failed it.

## Now Compress: writing the archives the corpus never had

**2026-08-15.** The format shipped with one real fixture, and the entry above
says what that cost: three of the five block shapes, the offset-delta search,
folders, data forks and multi-file archives were transcribed and never run.
The remedy is the M13 one — `tools/synth_now.py` writes the archives and
`unar` grades them, three ways: the bytes that went in, what the oracle
extracts, what we extract (`tools/run_now.py`, in `ci.sh`). Fourteen
archives, byte-exact on Linux and under qemu-m68k; thirteen are graded three
ways and the fourteenth one way, because on that one the reference is wrong
(the entry below). One of them, `synth-now-mixed.now`, is committed as a
fixture, so the differential suite grades these paths even where `unar` is
not installed.

**What the fixture actually reaches, measured rather than assumed.**
Instrumenting the block loop: three blocks, flags `0x40` twice and `0x20`
once, `padding` 0 everywhere, `delta` 0, no stream-restart record, no
"extra length" list, and the deepest Huffman code 12 of a possible 31. Every
one of those is now a generated archive, including a code 17 deep, which is
the only way the length-over-a-nibble list is reached at all.

**The oracle constrains what can be generated, and the constraint is a fact
about the oracle.** The first generated Huffman blocks failed in `unar` while
decoding perfectly here. XADMaster tracks its bit position as
`currbyte*8 - (numbits & 7)` and raises end-of-buffer the moment `currbyte`
passes the end, so it needs the stream's padding to cover whatever its
register is still holding — up to 7 bits. Bisecting confirmed it: 3 spare bits
or fewer and a block it otherwise reads is refused. Our reader is bit-serial
and never looks past the bit it needs, so it is strictly more tolerant, and
there is nothing to fix — but a generated archive the oracle cannot read
grades nothing, so the generator leaves a whole spare byte. `endbits` can
express at most 15 bits of padding, which is what bounds the workaround.

**An assertion that could not fail, again, and the same tell.** A zero-length
table record means "the next block starts a stream", which makes the decoder
reload the dictionary cache. Put that marker on the SECOND block and deleting
the code that reads it changes nothing — the cache was written after the first
block and still holds exactly what the running window holds. The suite stayed
green against a build with the marker ignored. On the THIRD block the two
differ and the mutant fails. **When a flag's effect is "restore state X", the
test only bites where X has since diverged** — which is the 2026-08-13 ration
assertion in different clothing: both observed a consequence that was true
anyway.

Twelve mutations of `fmt_now.c` were run against the suite and all twelve
fail it: fork order swapped, the delta search disabled, the dictionary restore
and the dictionary save each removed, the restart marker ignored, LZSS-only
folded into stored, Huffman-then-LZSS folded into Huffman-only, the new-LZSS
window based at the block start instead of the history, `padding` dropped from
the block length, directory nesting flattened, the extra-length list ignored,
and the word alignment after the code table.

**What none of it proves.** XADMaster is the only implementation of this
format in existence, so for the three shapes no real archive reaches,
agreement means the transcription matches its source — not that its source
matches Now Software. The two shapes the fixture does reach are graded against
a real archive by the differential suite, and that is the whole of the
external evidence. Written down in TESTING.md rather than left implied.

## Now Compress: an empty file in the middle, and which reader is right

**2026-08-15.** Generating archives turned up a shape the two
implementations decode differently, and it is the reference that is wrong.

**Claim:** a zero-length file anywhere but last makes `unar` mis-decode the
files after it. **Evidence:** an archive holding `two forks`, `empty`,
`after` and `beside` — `unar` reports `Folder/after` as failed and writes
`beside` at the right length with the wrong bytes; we extract all four
byte-exact. Moving `empty` to the end makes `unar` agree, which is how the
boundary was located. **Consequence:** asserted both ways in `run_now.py` —
our extraction must be exact and the oracle must still fail — so a later
`unar` that fixes this reports itself instead of quietly agreeing.

**The mechanism.** An empty file's stream has no blocks at all.
`produceBlockAtOffset` asks "have I run out of blocks?" with an `if` and not
a `while`, so after loading a header that declares zero it indexes
`blocks[0]` regardless — and the array is only reallocated when a file needs
MORE entries than the last one did, so `blocks[0]` still holds the previous
file's first block. The next file is then decoded from a stale offset.

Two things worth carrying:

- **Reading per file made this unreachable rather than fixed.** Nothing in
  `fmt_now.c` handles it; the stream is opened per file, from that file's own
  table, so a file with no blocks is simply a file whose table is never read.
  The solid abstraction the entry above declined to inherit is exactly where
  the bug lives. **An architecture that cannot represent a bug beats a check
  for it.**
- **The oracle failed loudly on one entry and SILENTLY on the next.**
  `beside` came back the right length with the wrong bytes — no error, no
  warning. A differential suite that only compared exit statuses would have
  called that a pass, which is the same lesson the emulator harness taught on
  a different day: the dangerous failure is a wrong verdict, not an error.

## Two corpus lines that could not be restored, found by adding a third

**2026-08-15.** Committing a generated Now Compress archive as a fixture meant
writing a `synthetic:tools/synth_now.py` line in `fixtures/SOURCES.md`, and

## The second Now Compress archive, found by creator code

**2026-08-16.** OPEN_ITEMS.md asked for one thing: another real Now Compress
archive. It exists, it was on a public mirror the corpus already draws from,
and **no filename search would ever have found it**.

**What the name search says.** `.now` is the extension (the format's users say
so; there is no other public description). Crawled and searched by name:
funet's whole `/pub/mac` tree — 45,891 files, 30,596 of them `.hqx` — has no
`.now` anywhere; umich's 3,678 do not either; the Wayback Machine has never
archived a `.now` URL on any of six Mac hosts (`hyperarchive.lcs.mit.edu`,
`sumex-aim.stanford.edu`, `mac.archive.umich.edu`, `ftp.amug.org`,
`www.macgurus.com`, `ftp.apple.com`), and the same query for `.hqx` on the
first of them returns results, so the filter works. Now Software's own site is
in the Wayback Machine with no binaries. Their updaters are `TEXT/NwUD` and
`APPL/RMSP`, not Now Compress. Now Utilities 6.5's CD ships a 531-file HFS
listing with type and creator for every file and not one `NC` creator among
them, because Now Compress was 5.x-era and did not survive into 6.

**What found it is 4 bytes of metadata.** A Now Compress self-extracting
archive is an application with creator **`NCse`**, and BinHex and MacBinary
both carry type and creator in a header near the front of the file — so a
2 KB range request per file, decoded, gives the creator of every archive on a
mirror for a few megabytes of traffic. 241 `.sea`/`.bin` files into that
sweep: `science/SyntheticReferences2.0.sea.bin`, 1995, 2,960,000 bytes,
`APPL/NCse`. **The format is invisible in filenames and obvious in four bytes
of Finder metadata; search the metadata.**

**The specimen.** A folder, a `TEXT/ttxt` file with both forks (574 B data,
332 B resource) and a 9,949,696-byte FileMaker Pro database, in 2.9 MB. Two
streams, 306 blocks, all of them "new" LZSS with flag bit `0x100` also set
(which this decoder ignores and the reference ignores too), no padding, no
offset delta, and **two stream-restart records** — the zero-length table entry
that reloads the dictionary cache, which the corpus's first fixture never
uses and which had only ever been exercised by generated archives. Peak heap
on the 9.9 MB extraction is 131,072 B: the flat 128 KB holds.

**`unar` cannot read it.** Every fork fails with "Attempted to read more data
than was available", on the raw `.sea` and through the MacBinary envelope
alike. The cause is the overrun derived the day before from generated
archives: XADMaster tracks its bit position as `currbyte*8 - (numbits & 7)`
and raises end-of-buffer as soon as `currbyte` passes the end, so it needs the
padding to cover its register — up to 7 bits. **129 of this archive's 306
blocks end with fewer than 7 spare bits**, and the spare count is spread
almost uniformly over 0..15, i.e. the real encoder pads to the word and no
further. So the workaround in `tools/synth_now.py` — always leave a spare byte
— is a departure from what real archives look like, and the reason it exists
is now measured on a real one rather than inferred. What was written up as "a
property of the oracle rather than of the format" is stronger than that: it
makes the only implementation of this format unable to read the format.

**Why we believe our output, given nothing can grade it.** Three
independent things, none of which is our own say-so: the 574-byte `TEXT` fork
is coherent English prose describing the product it ships with; the 332-byte
resource fork's own first 16 bytes — data offset 0x100, map offset 0x11A, data
length 0x1A, map length 0x32 — account for exactly 332 bytes, and a resource
fork identifies itself that way; and the entry table's declared sizes are met
exactly. `tools/run_now.py` asserts the structural one, which can fail on its
own terms: swap the fork order and it reports a resource fork that is not one.
The hashes beside it are labelled for what they are — a regression anchor, not
ground truth.

**Consequences for the corpus.** Two fixtures joined it (the envelope and the
derived archive), the suite is 809, and **four forks are adjudicated by
nobody** — the manifest carries names, type and creator from `lsar`, which
walks the archive fine, and marks every fork unadjudicated with the oracle's
own error. That is the same shape as DiskDoubler's 11 (OPEN_ITEMS.md), and it

**The transferable part.** A format whose files are rare is not necessarily a
format whose files are gone: this one had been sitting on the mirror this
project has harvested since M0, three directories away from fixtures already
in the corpus. What hid it was that every search anyone would run — the
extension, the product name, the vendor — is a search over names, and the
thing that identifies it is metadata. **When a format is defined by its
header, look for it with its header.**
