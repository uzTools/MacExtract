| M11 Multi-segment archives | **DONE (three schemes)** | StuffIt segments (`B0 56 00`, XADMaster's "StuffIt split file") join end to end: engine joiner over an `UncVolumeSource` callback, CLI auto-discovery + `--part`/`--ask`/`--no-parts`, Mac "locate part N" alert offering Standard File. **Parts are identified by their header — name bytes plus 26 fingerprint bytes — never by filename**, which is what makes a set work when its parts are scattered or named unlike each other; `unar` cannot read such a set at all, since its own discovery is gated on a name prefix (DECISIONS.md). 7 synthetic cases adjudicated three ways (generator, `unar`, us) in `ci.sh`, plus mutation-proofs that the suite fails. **On a real emulated Mac Plus: byte-exact at 4 MB and at the 1 MB floor**, with a missing part returning `UNC_ERR_SEGMENTED` — the first code path in the project to produce that error, declared since M0 and until now returned by nothing. The join is read **strictly forward (0 backward crossings, measured)**, so no part is ever asked for twice. The "locate part N" dialog itself was driven on System 6 on 2026-08-09 (`interactive.py --segments`) — wrong part refused and named, right one accepted, joined file read back byte-exact; both bugs that phase found were in the harness and both looked like application bugs (DECISIONS.md). **Spanned ("split") zip is the second scheme, added 2026-08-09**, engine and Linux CLI only. `NAME.z01` … `NAME.zip` concatenate with no header to strip, and the archive addresses itself as (part, offset within that part). Only its first and last parts identify themselves at all — and the last is the only place the part COUNT is written — so the host orders parts by NAME and the engine adjudicates the assembled set structurally: part count against the end-of-central-directory record, the central directory's position, every entry's local header, every CRC-32. **Names propose, content disposes**; that those checks are load-bearing was established by building a deliberately lax reader and confirming the suite's *wrong order* and *foreign part* cases are exactly the two that then pass (DECISIONS.md, TESTING.md). 5 generated sets adjudicated FOUR ways in `ci.sh` — the source tree, `unar`, us on the set, and us on the same content zipped unsplit, which owes nothing to the joiner. **The set is read in the fewest part opens the format allows** (6 with 1 backward crossing on a 5-part set, 14/2 on a 12-part one), which `ci.sh` derives independently from each archive's own directory and requires to match: the parts are addressed as the (part, offset) pairs the format stores rather than flattened into one stream, and the directory is read once instead of between every entry. The first version cost 22/7 and 49/14 and was written up as the format's doing; it was not (DECISIONS.md 2026-08-09). Two side effects worth their own lines: `zip -s` writes its marker even when the archive did not need splitting, and such a file used to sniff as *unknown* and could not be extracted at all — it now reads as the ordinary zip it is; and every zip lost the 66,000 B tail buffer it allocated to find its directory record, so zip's peak heap is now 12–54 KB on Linux and **12–53 KB on a real emulated Mac Plus**, re-measured (FORMATS.md ¶). **Plain `.NNN` splits are the third scheme, added 2026-08-10**, engine and Linux CLI only. A part carries no header, no marker and no part count — the scheme IS the naming convention (`reference/XADMaster/XADSplitFileParser.m`) — so the descriptor is built by the HOST and `unc_segment_describe` never returns it; the joined LENGTH is the sum of the parts', which is why every part is located before extraction starts rather than disk by disk. **What adjudicates such a set is the file it joins back into**, and how far that goes was measured rather than assumed: a swap of two parts of a split zip is thrown out by the payload's own offsets and CRCs *unless the swap involves part 1*, after which the join no longer looks like an archive and nothing objects. Both halves are asserted in `ci.sh` (DECISIONS.md 2026-08-10). Discovery decides by NAME **before** the sniff, deliberately: `unar` tries its content parsers first, so `unar Archive.sit.001` reads the truncated StuffIt it is a slice of and exits 1 — the shape these sets actually have in the wild is one the reference cannot read. Two departures from that reference, both re-measured every run: the run must be consecutive from `.001`, and a member numbered past its end is a missing part rather than another part (the reference appends a stray `NAME.900` silently, 10,200 → 10,208 B). 3 generated cases in `ci.sh`, adjudicated against the original bytes, against `unar` where it can join at all, and — for the archive payload — against our own read of the unsplit archive. **Per-part envelopes are the fourth piece, added 2026-08-13**, engine unchanged and Linux CLI only: `Archive.sit.1.hqx` — every part BinHex- or MacBinary-encoded on its own, which is how a set was actually distributed — joins, because the envelope now comes off each part BEFORE the join instead of after it. Only the StuffIt scheme is looked for that way, since its identity is in the payload and survives the wrapper, where the other two are placed by a filename the wrapper replaces. The search is rationed by NEED rather than by shape: envelopes beside the archive are opened only while the set is still short of a part (`seg_have_all` sums located payloads against the fork lengths the header states), which costs a complete set nothing and makes a half-unstuffed set — some parts already unwrapped, one still in its envelope — join as a side effect nobody designed. 3 generated cases in `ci.sh` adjudicated by the generator, by our own read of the same set unwrapped, and by what `unar` does with one: it unwraps the single part it was handed and exits 0, success with a fragment. All four new assertions were shown to fail before being believed, including the ration's, whose first version could not (DECISIONS.md 2026-08-13, TESTING.md). **Compact Pro segments are the fourth scheme, added 2026-08-14**, engine and Linux CLI only — and the first format here whose layout is DERIVED rather than transcribed, because no reference implementation reads it and no sample existed. Both were solved the same way: `tools/vmac/cptsegment.py` drives Compact Pro 1.51 itself on System 6.0.8 under Mini vMac and cuts a real segmented set out of an archive the differential suite already adjudicates. Every segment carries the same 8-byte header an ordinary archive has, with a 16-bit set identity shared across the set and an index offset that is 0 in all but the LAST segment — the byte-level form of the author's manual saying names do not matter and the final segment is the one you open. **Identity is content, so any segment opens the set**, which the application itself cannot do. Entries are addressed as (volume, offset within that volume), so this reads in the same addressed mode as a spanned zip, with one difference that cost 2 of 11 entries until it was found: rolling into the next part starts after its 8-byte header. The index is buffered for the walk — 19 part opens with 8 backward crossings become 5 and 1 — and that buffer is allocated LAST so a refusal costs crossings rather than the extraction. `tools/synth_cptsplit.py` writes the layout in Python and is required to reproduce both real specimens byte for byte. Reacting to a disk insertion, and the three schemes still missing from the Mac shell, are scoped out and ranked in OPEN_ITEMS.md section 4. |
